# Project brief — Serve the admin and the catalogue on the deployment's own domain

The mandate is [#293](https://github.com/yedeya/plinthos/issues/293), the Owner's decisions of 2026-11-04. It is the change brief #6's decision 8 deferred: a custom domain as optional configuration. The brief adds a section to `docs/qa/specs/platform.md`, `[PLAT-17]` to `[PLAT-19]`, two clauses to `docs/qa/specs/publish.md`, `[PUB-21]` and `[PUB-22]`, and `[PHOTO-10]` to `docs/qa/specs/photos.md`. It adjusts `[PLAT-1]` for the `us-east-1` certificates, `[PUB-1]` for the second origin on the same bucket, and `[PUB-6]` for the second path form. Every clause is `[seed]`. Examples use `example.com` throughout: a deployment's real names live only in its configuration (`AGENTS.md`'s constraints, a public repository).

## 1. The real problem

**Both hosts are CloudFront's, and nothing in the stack knows of another name.**
- **The admin:** `sst.aws.Nextjs` with no `domain` (`git grep -n "new sst.aws.Nextjs" -A3 infra/admin.ts`). Its header comment still cites "no custom domain (brief #6, decision 8)".
- **The catalogue:** a raw `aws.cloudfront.Distribution` with `cloudfrontDefaultCertificate: true` and no aliases (`git grep -n "viewerCertificate\|aliases" infra/snapshot.ts`).
- **The configuration:** no domain setting (`git grep -n "name: 'PLINTHOS_" infra/config.ts`). `[PLAT-2]` already foresees "a domain if one is used".

**What SST v4 offers, read from the installed platform (`sst` 4.17.2; `.sst/platform/src/components/aws/` after `npm run typecheck`):**
- **`sst.aws.Nextjs`'s `domain`** goes to its `Cdn`, which creates a DNS-validated ACM certificate in `us-east-1`, puts the name on the same distribution as an alias, and adds A and AAAA alias records through `sst.aws.dns()` (`grep -n "createSsl\|createDnsRecords\|useProvider" cdn.ts`). The distribution is updated in place, not replaced, so its `cloudfront.net` host stays the same.
- **With a domain set, SST blocks the admin's `cloudfront.net` host.** It adds `CF_BLOCK_CLOUDFRONT_URL_INJECTION` to the viewer-request function, which answers 403 to any host containing `cloudfront.net` (`grep -n "blockCloudfrontUrlInjection" ssr-site.ts`). It runs after the admin's own injection, which only sets two headers (`[AUTH-14]`), so that injection is unaffected.
- **`admin.url` becomes the domain's address** once one is set (`grep -n "domainUrl ?? distribution" ssr-site.ts`). The photo bucket's CORS rule (`git grep -n "allowUploadsFrom(admin.url)" infra/stack.ts`), the `adminUrl` output and the smoke check all read it, so they follow the name with no code of their own (`[PHOTO-10]`, `[PLAT-19]`).
- **`sst.aws.dns()`** finds the hosted zone by the record's name when no zone id is given (`grep -n "HostedZoneLookup" dns.ts`). The catalogue's raw distribution gets no `domain` option: it needs its own certificate, validation records and alias records, built from the same pieces.

**The same-origin check already follows the name.** `[AUTH-7]` compares `Origin` with `x-forwarded-host`, which SST's viewer-request function sets from the viewer's `Host` (`git grep -n "x-forwarded-host" src/server/auth/origin.ts`). It holds no configured host, so no auth code changes. The session cookie is `__Host-`, bound to the host that set it (`git grep -n "__Host-" src/server/auth/cookie.ts`), so the owner signs in again on the new name.

**The catalogue's path holds a `c/` the mandate's address doesn't.**
- **Today's address** is the distribution's host followed by `/c/{token}/` (`git grep -n "return \`/\${SNAPSHOT_PREFIX}" src/server/publish/snapshot.ts`). The bucket policy grants reads only under `c/` (`[PUB-1]`, `[PUB-2]`).
- **The mandate's address** is `https://catalogue.plinthos.example.com/{token}/`. Serving it needs the request path mapped onto `c/` in the bucket. This must not break the links already shared under `/c/`.
- **The two path forms** (`[PUB-21]`): an origin whose path is `/c` serves the default behaviour, and a `/c/*` behaviour keeps today's origin. Both forms work on every host the distribution answers at. It costs nothing, and no function runs on the public path.
- **Invalidation is per viewer path**, so a publish has to invalidate both forms (`[PUB-6]`, `[PUB-22]`). Today it invalidates two paths per publish (`git grep -n "invalidate(\[" src/server/publish/publish.ts`), and it will invalidate four.
- **The pages' own links are relative** (`git grep -n "relative" src/server/publish/snapshot.ts`), so a page works under either form.

**The first deploy has an ordering trap.** ACM can't validate a certificate until the parent domain delegates to the zone. A deploy run before the Owner adds the NS records at the parent's provider waits on the certificate validation, then fails. Hence decision 6: the zone exists, and its delegation answers, before the first deploy that sets the domain.

**The phone holds state per origin.** The offline queue (`[SYNC-7]`) and the set index (`[CAT-10]`) live in IndexedDB, which belongs to an origin. The installed web app's scope is its origin too (`git grep -n "scope" src/app/manifest.ts`). Once the old admin host answers 403 (`[PLAT-19]`), a queue left there can't sync and can't sign out, since sign-out needs the server (`[SYNC-9]`). Hence the switch steps (decision 9).

## 2. Scope

**This project is:**
- `PLINTHOS_DOMAIN`, one optional setting, read and validated in `infra/config.ts` (`[PLAT-17]`);
- the admin at the domain, and the catalogue at `catalogue.` followed by it, each with its own certificate, in a hosted zone the stack looks up (`[PLAT-18]`);
- the old admin host closed (`[PLAT-19]`), and the photo bucket's CORS rule following the admin's address (`[PHOTO-10]`);
- the catalogue at `/{token}/` as well as `/c/{token}/`, with the address the admin shows in the first form (`[PUB-21]`, `[PUB-22]`);
- `docs/deploy.md`: the setting, the zone and its delegation, the order of the first deploy, the phone's switch, going back, and the teardown;
- `docs/observability.md`'s rows, and a dated pass in `docs/security-review.md`.

**It is not:**
- **The zone itself.** The Owner creates it by hand, once, and adds its NS records at the parent's provider (decision 6, Issue D). The stack never manages it.
- **Moving the parent domain's DNS to AWS.** That stays with its current provider (decision 3).
- **More names.** There is no `www`, no apex redirect, no extra alias, and no way to name the two hosts apart. One setting gives both names (decision 4). A deployer who needs other names would bring this back.
- **A redirect from the old hosts.** The admin's old host answers 403, as SST does. The catalogue's old host keeps serving, because a redirect would add a function to the public path for no gain (decision 8).
- **The admin's security headers** (F-3: HSTS, CSP, framing). The custom name doesn't change what they protect. The dated pass re-grades F-3 with the new name in mind, and a fix is its own item if it is filed.
- **The deploy lane's workflow.** `docs/deploy.md`'s lane table gains a `PLINTHOS_DOMAIN` row. The lane can't deploy yet (its known gap, yedeya-labs/kanon#1555), and nothing under `.github/` changes here.
- **A schema change or a migration.**

## 4. Cost

**About $0.50 a month with a domain set, and $0 without one.** The Owner approved the zone on 2026-11-04 (decision 2). This is one environment, the one stage (`[PLAT-1]`), at Route 53's and ACM's list prices as recalled (§8):
- **The hosted zone:** $0.50 a month. It is billed while the zone exists, set or unset, until the Owner deletes it.
- **DNS queries:** alias queries for a CloudFront distribution are free. The rest, such as NS, SOA and ACM's validation lookups, cost $0.40 per million, so a fraction of a cent.
- **The certificates:** public ACM certificates are free, renewals included.
- **The second origin and the `/c/*` behaviour:** free.
- **Invalidations:** four paths a publish instead of two. The first 1,000 paths a month are free, which covers 250 publishes.
- **No alarm** (§5), no function, no schedule, no new bucket and no new distribution. Nothing touches Aurora (`[PLAT-7]`).
- **At rest,** the stack's about $0.77 a month (brief #6, §4) becomes about $1.27, well under the $10 target.

## 5. Observability

- **Skip, not paged: `domain.certificate.renewal`.** ACM renews a DNS-validated certificate by itself while it is in use and its validation record is still in the zone. Every deploy puts the record back. A renewal that fails raises an AWS Health event ahead of expiry (recalled, §8). An alarm on ACM's `DaysToExpiry` would cost about $0.10 a month for each certificate. It would also have to live in `us-east-1`, with a second SNS topic there, for a failure that gives weeks of warning. *What would change the answer:* a renewal that is seen to fail, or the catalogue link shared with buyers in selling mode, where an expired certificate would turn visitors away unseen.
- **Skip, not paged: `domain.delegation`.** If the parent's NS records are removed or changed, both names stop resolving. Nothing on AWS sees it, and only an external probe could, which `health.live`'s row already declines. The next deploy's smoke check fails on it, because `adminUrl` is the domain's (`[PLAT-4]`, `[PLAT-19]`). *What would change the answer:* the same trigger as `health.live`'s.
- **No new log event.** Nothing in the app's code changes behaviour by host, so there is nothing new to log.
- Both rows go into `docs/observability.md`'s not-paged table (Issue A). The zone and the NS records go into its hand-created table (Issue D).

## 7. Decisions

Answered by `@yedeya`, as Owner, on 2026-11-04, in the mandate:

1. **Two names. ✅ ANSWERED (Owner, 2026-11-04): the admin at `plinthos.example.com/admin`, the catalogue at `catalogue.plinthos.example.com/<token>`.** One name per distribution keeps the two origins apart, so decision 15 of brief #6 and `[PUB-1]` hold by construction. Carried into `[PLAT-18]` and `[PUB-22]`.
2. **The zone. ✅ ANSWERED (Owner, 2026-11-04): a delegated Route 53 hosted zone for the base name in the Plinthos member account, about $0.50 a month.** Carried into §4 and `[PLAT-18]`.
3. **The parent's DNS. ✅ ANSWERED (Owner, 2026-11-04): it stays with its current provider; the Owner adds the zone's NS records there once.** Carried into Issue A's `docs/deploy.md` section and Issue D.
4. **Optional, one setting. ✅ ANSWERED (Owner, 2026-11-04): unset keeps today's `cloudfront.net` hosts at no added cost; one base-domain setting gives both names.** Carried into `[PLAT-17]`.

The Lead's technical decisions (`K-PROJ-18`):

5. **The setting. ✅ ANSWERED (Lead, technical): `PLINTHOS_DOMAIN`, holding the admin's name, which is also the zone's name.** Its validation is `[PLAT-17]`'s. The catalogue's name is derived as `catalogue.` followed by it, never set apart. A name under `cloudfront.net` or `amazonaws.com` is refused, because neither can be delegated to the deployment. The value is lowercased rather than refused for capitals, since DNS names don't distinguish case.
6. **The zone's lifecycle. ✅ ANSWERED (Lead, technical): created by hand, once, and only looked up by the stack.** The NS records at the parent name the zone's own four name servers. A zone the stack created would be deleted by `sst remove`, or replaced by a rename, and come back with new name servers, so the delegation would break silently and the next certificate validation would hang. `removal: 'retain'` keeps buckets and tables, and a zone is neither. Made by hand, the zone outlives a teardown, and the delegation can be checked before the first deploy that needs it, which settles the ordering trap (§1). It is recorded as a hand-created resource (`K-OBS-8`). The rejected option was the stack creating it with `protect` and `retainOnDelete`: on the first deploy the name servers would appear only after the deploy started waiting on them.
7. **CORS and the origin check. ✅ ANSWERED (Lead, technical): both follow the admin's one address with no setting of their own.** CORS reads `admin.url` (`[PHOTO-10]`). `[AUTH-7]` compares with the host the browser asked for, so `src/server/auth/` doesn't change, and no AUTH clause is added.
8. **The catalogue's path. ✅ ANSWERED (Lead, technical): both `/{token}/` and `/c/{token}/`, by a second origin with origin path `/c`.** The address the admin shows is the short one, on every host (`[PUB-22]`). The rejected options: keeping `/c/` in the new address, which is not the mandate's; a CloudFront Function that rewrites or redirects, which puts code on the public path and is billed per request; and moving the bucket's prefix, which would break `[PUB-1]`'s policy and every shared link. **The trailing slash is part of the address.** `/{token}/` serves the catalogue; `/{token}` without the slash maps to the key `c/{token}`, which doesn't exist, and gets S3's 403, as `/c/{token}` does today. The admin always shows and copies the address with the slash, so shared links work; a hand-typed address without it does not. Adding the slash for the visitor would need a CloudFront Function, which this decision rejects.
9. **The switch, for the phone and for old links. ✅ ANSWERED (Owner, 2026-11-04): as proposed.** The old admin host answers 403, each device syncs and signs out first, an unsynced device is recovered by unsetting the domain, and old catalogue links keep working until a token rotation. What was proposed:
   - **The admin's old host answers 403.** This is SST's own behaviour once a domain is set, so the admin has one origin, one CORS origin and one cookie host (`[PLAT-19]`).
   - **Before setting the domain**, each device syncs until `/admin` lists nothing waiting, signs out, and removes the installed app. The queue and the set index belong to the old origin, and once that origin answers 403 a device can neither sync nor sign out.
   - **If a device was not synced,** unset the variable and deploy; the old host answers again. Sync and sign out on that device, then set the variable again.
   - **The catalogue's old host keeps serving,** in both forms, so every link already shared keeps working until the Owner rotates the token (`[PUB-15]`), which ends it everywhere. The bytes are the same and the token is the capability, so this adds no exposure.

   The alternatives: keep the old admin host open beside the new one (two origins, two sessions, and a CORS rule for both, for a convenience that only lasts while the switch is happening); or retire old catalogue links at the switch, which a rotation already does when the Owner wants it. Carried into `[PLAT-19]`, `[PUB-22]`, Issue A's `docs/deploy.md` steps and Issue D.
10. **HSTS on the catalogue. ✅ ANSWERED (Lead, technical): unchanged.** The snapshot's response-headers policy already sends `includeSubDomains` (`git grep -n "includeSubdomains" infra/snapshot.ts`). On `catalogue.plinthos.example.com` it covers only names under that name, never the admin's name or the parent domain, so it constrains nothing the deployment doesn't control. The admin sends no HSTS (F-3), and Issue C re-grades that.
11. **Signals. ✅ ANSWERED (Lead, technical): no alarm; two not-paged rows.** See §5. An alarm would raise spend, which would be the Owner's to approve, and this brief asks for none.
