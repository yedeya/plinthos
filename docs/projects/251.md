# Project brief — Filters on the admin item list: theme, condition, complete, instructions, kind, needs attention, and sort

The mandate is [#251](https://github.com/yedeya/plinthos/issues/251): the Owner's request of 2026-11-03 to filter the item list on `/admin` by "category such as pirates or ninjago", by condition, and by complete and instructions yes or no. The Owner asked what else would make the search more useful. The rest of this brief is the Lead's proposal, and its decisions are open until the Owner answers them. The brief adds ten clauses to `docs/qa/specs/items.md` (`[ITEM-11]` to `[ITEM-20]`) and adjusts `[ITEM-8]`. Every clause is `[seed]`. Like #226 and #233, this is a compact brief, built by local agents.

## 1. The real problem

**The list on `/admin` has one filter, a text box.**
- **What it matches:** the set number, the name and the reference number (`[ITEM-8]`, `git grep -n "export function matchesFilter" -A5 src/app/_offline/items.ts`). Nothing else.
- **What the list holds:** the kind, the condition and the quantity, but not the theme, completeness, instructions, year or photos (`git grep -n "export interface ListedItem" -A20 src/app/_offline/items.ts`). The page can't filter on what it never loaded.

**A "Ninjago" filter on today's theme would miss sets.**
- `lego_set.theme` is Rebrickable's leaf theme, by name only. No theme id and no parent is stored (`git grep -n "theme" src/db/schema/lego-set.ts`).
- Rebrickable's themes are a tree. A set filed under a sub-theme carries the sub-theme's name, not Ninjago's.
- The client already fetches Rebrickable's whole theme list in one request when it needs several names (`git grep -n "lego/themes" src/server/catalogue/rebrickable.ts`). That list carries each theme's parent, which the client reads past today.
- So the top-level theme needs a column, filled on every lookup and search (`[ITEM-11]`, `[ITEM-12]`), and a backfill for the sets already stored (`[ITEM-13]`).

**The backfill can't simply map names.** Without a stored theme id, the backfill has only the leaf's name. A name can occur under more than one parent in Rebrickable's tree, so a name alone can be ambiguous. The rule: a name that occurs once is mapped with no request, and any other set is looked up by its number, one request each (`[ITEM-13]`).

**The overview reads every item in one query.**
- `listItems` has no limit and no paging (`git grep -n "limit(\|readPaged" src/server/items/items.ts` finds nothing).
- A Data API answer stops at 1 MB. The parts code reads 2,000 narrower rows a page to stay under it (`git grep -n "LOT_PAGE =" src/server/parts/lots.ts`). An item row is wider, and this project widens it again.
- So a large collection would fail the whole page, not just its filters. `listItems` reads in pages (`[ITEM-20]`).

**What the data supports, for "needs attention":**
- **No photo:** yes, from the item's photos.
- **No value:** yes, from the values the list already shows (`[VAL-7]`).
- **Incomplete with nothing noted:** yes, from `complete` and `missing_notes`.
- **Hidden from the catalogue:** no. No item can be hidden: the projection reads every item, and `collection_item` has no such column (`git grep -n -i "hidden\|visib\|publish" src/db/schema/collection-item.ts` finds nothing). This filter is left out.

**"Not recorded" fits two filters, not three.** Completeness and instructions are null for a non-set that stated neither (`[ITEM-10]`). Condition is required for every item (`[ITEM-1]`), so it has no "not recorded".

## 2. Scope

**This project is:**
- the theme id and the top-level theme on `lego_set`, filled on every lookup and search, and backfilled for the sets items name;
- filters on `/admin` for theme, condition, completeness, instructions, kind and needs attention, with a count on each option;
- a sort by date added, value or year;
- the filters and the sort in the page's query string;
- the same filters over the items still in the device's queue;
- a paged `listItems`.

**It is not:**
- **Filters on the public catalogue.** A theme or kind filter there would be computed from the snapshot alone, so nothing private can leak through a count (`AGENTS.md` §1). It is a later project. `top_theme` is classified public so that project can publish it.
- **A faster set search.** Another brief covers it: a local index of Rebrickable's data files. That index could later supply the theme tree with no request. This brief doesn't depend on it, and uses the Rebrickable client as it is.
- **A per-item "hide from the catalogue".** It doesn't exist, so it can't be filtered on. Building it is its own project.
- **Filtering on the server.** The list is filtered in the browser (decision 7). Section 8 says when that would need revisiting.
- **The offline shell's list.** It shows only the queue, with no server data (`[SYNC-6]`), and keeps no filters.
- **A change to the text filter beyond theme names.** It still matches the set number, the name and the reference number, and now the theme too.

## 4. Cost

**$0 a month more.**
- **Filtering, counts and sort** run in the browser. They send no request and wake nothing.
- **The paged read** adds one Data API request per extra page, only for a collection past one page. That is a fraction of a cent a month.
- **The backfill** is one theme-list request plus one request per owned set whose theme name is ambiguous or unknown. It runs inside the migration step, which already keeps Aurora awake for about six minutes (`docs/deploy.md` step 5). A few hundred lookups at one a second add a few minutes once, under a cent. Every later run finds nothing to fill and makes no request.
- **Rebrickable** is free, within its rate limit, which the client keeps (`[CAT-2]`).
- **No resource, no schedule and no alarm** (`AGENTS.md` §3).

## 5. Observability

- **Add, not paged:** `catalogue.themes.backfilled`, with how many sets were filled by name, filled by lookup, and left unknown. It runs during a deploy someone is watching. A set left unknown shows on `/admin` as *Theme not known*, and the next deploy tries it again. What would change the answer: a backfill that runs on a schedule, with nobody watching.
- **No new signal for a failed lookup.** `catalogue.lookup.failed` already logs every Rebrickable failure with its reason (`docs/observability.md`).
- **No signal for the filters.** They run in the browser and fail only in front of the owner.
- **No alarm.** Each would cost about $0.10 a month, for a failure the owner sees on the page.

## 6. Blast radius — what will need a human

- **Issue A:** `src/db/schema/` (`schema`) and `drizzle/` (`migrations`). The migration only adds nullable columns, so it may also run before the deploy, as #204's did.
- **The release between them.** Issues B and C read or write Issue A's columns, so they merge only after a release carries Issue A (`docs/qa/stack.md`'s `## Schema changes`). The Owner cuts that release. Until then the Reviewer holds them.
- **Issue B:** `scripts/migrate.ts` and `docs/deploy.md`. Neither is an escalation path. The step gains its first outbound request, and the deploy lane's migration then needs the Rebrickable secret, which `sst shell` already hands it with the others (section 8).
- **Issue C:** `src/server/items/` and `src/app/`. Neither is an escalation path. `listItems` answers whether a note of what is missing exists, never the note, and still no storage location (`[ITEM-20]`).
- **No change to the projection, the publish step, auth, uploads or `infra/`,** so no security pass is due.

## 7. Decisions

1. **The filters the Owner asked for. ✅ ANSWERED (Owner, `@yedeya`, 2026-11-03): theme, condition, complete, and instructions yes or no,** on the item list on `/admin`. Carried into `[ITEM-14]`.
2. **What "theme" means. PROPOSED (Lead), awaiting the Owner: the top-level theme.** Choosing Ninjago lists every Ninjago set, whatever its sub-theme. The options: (a) the top-level theme alone, recommended, because it is what "pirates or ninjago" asks for; (b) today's leaf theme alone, which misses sets under a sub-theme; (c) both, a top-level theme and then a sub-theme, which doubles the controls on a phone. The text filter matches both names either way, so typing a sub-theme still finds its sets. Carried into `[ITEM-11]` and `[ITEM-14]`.
3. **A kind filter. PROPOSED (Lead), awaiting the Owner: set, minifigure, bulk lot and other.** Carried into `[ITEM-14]`.
4. **"Needs attention". PROPOSED (Lead), awaiting the Owner: no photo, no value, and incomplete with nothing noted.** *Hidden from the catalogue* is left out, because no item can be hidden. The no-value filter and the value sort read values, which are private, but the list is admin-only (`[VAL-7]`), so they leak nothing. Carried into `[ITEM-15]`.
5. **The sort. PROPOSED (Lead), awaiting the Owner: date added, value or year, each in one direction.** Newest added first (today's order, the default), highest value first, newest year first. Items without a value or a year come last. A reverse order for each is easy to add if the Owner wants it. Carried into `[ITEM-16]`.
6. **Counts and the URL. PROPOSED (Lead), awaiting the Owner: a count on each option, and the filters in the query string.** A count says how many items that option would list with the other filters as they are. The query string is what makes going back from an item, a reload and a bookmark keep the filters. Carried into `[ITEM-17]` and `[ITEM-18]`.
7. **Filtering in the browser, queued items included. PROPOSED (Lead), awaiting the Owner: the page filters what it loaded.** It is instant, costs nothing and keeps working when the network drops. The queue doesn't know a queued set's theme, so a queued set shows under every theme, and a filter never hides unsynced work. The alternative is filtering on the server, which would need a request per tap and wouldn't work offline. Carried into `[ITEM-14]` and `[ITEM-19]`.
8. **When the backfill runs. PROPOSED (Lead), awaiting the Owner: in the migration step, after the migrations.** Every deployment then fills its themes on the next deploy, with nothing to remember, and later deploys find nothing to do. The alternative is a separate command in `docs/deploy.md` that each deployer runs once by hand, which keeps outbound requests out of the migration step but can be forgotten. Carried into `[ITEM-13]`.
9. **The Lead's technical choices. ✅ ANSWERED (Lead, technical, `K-PROJ-18`):**
   - two columns, `theme_id` and `top_theme`, rather than a themes table: the tree is Rebrickable's, and the client already caches it;
   - the backfill maps a unique leaf name with no request, and looks up any other set by its number, so an ambiguous name is never guessed;
   - the backfill fills only sets an item names, because searches store many sets nobody owns, and those fill on their next fetch (`[ITEM-12]`);
   - `listItems` reads in pages, and answers a boolean for the missing-parts note, never the text;
   - the query string is written with the History API, so a filter change makes no request and no server render;
   - an option is shown with its count, even at 0, so the controls don't jump as the owner taps.

## 8. What I did not examine

- **The size of a large collection's page.** The 1 MB cap is per Data API answer, and the paged read removes it. The page itself still sends every item to the browser. I did not measure where a phone slows. A guess is several thousand items. Past that, filtering on the server, with the query string as its input, is the next step.
- **Duplicate theme names in Rebrickable's tree** are recalled, not counted. The backfill's rule is safe either way: it never maps an ambiguous name.
- **The theme list's size.** The client asks for 1,000 themes in one page. I recalled that Rebrickable has fewer, and did not check for a `next` page. Issue B checks it.
- **`parent_id`** on Rebrickable's theme answer is recalled from its API, not re-read.
- **`sst shell` handing the Rebrickable secret to `scripts/migrate.ts`** is inferred from it handing the session secrets today. Issue B confirms it, in a local run and in the deploy lane.
- **The number of owned sets** in the reference deployment, and so the backfill's request count there, was not counted. No collection data is in the repository.
- **The layout of the filter controls on a phone** is sketched, not designed. Issue C's PR shows it.
