# Project brief — A set search index on the phone, built weekly from Rebrickable's downloads

The mandate is [#252](https://github.com/yedeya/plinthos/issues/252), the Owner's decisions of 2026-11-03. The brief adds a section to `docs/qa/specs/catalogue.md`, `[CAT-6]` to `[CAT-11]`, and adjusts `[ITEM-9]` for the offline shell. Every clause is `[seed]`. Like #226 and #233, this is a compact brief, built by local agents.

## 1. The real problem

**Every name search waits for Rebrickable.**
- **The search:** `searchSets` reads `lego_set` first, and then asks Rebrickable's search for anything but a fresh, typed set number (`[CAT-3]`, `src/server/catalogue/sets.ts`).
- **The limit:** every Rebrickable call waits behind one request a second per server instance (`[CAT-2]`). A search that meets a theme the instance has not seen adds a theme lookup, so one answer can cost two calls.
- **The table is small:** `lego_set` holds only the sets this deployment has already looked up. #200 made the search local first, but a set the owner has never entered is never local.
- **Offline:** the field sends no request without a network or on the offline shell (`[ITEM-9]`), so it can only take a typed set number.

**What the downloads hold** (fetched on 2026-11-03; re-run with `curl -sI https://cdn.rebrickable.com/media/downloads/sets.csv.gz`):

| File | Compressed | Rows |
|---|---|---|
| `sets.csv.gz` | 523 KB | 28,565 |
| `minifigs.csv.gz` | 305 KB | 17,363 |
| `themes.csv.gz` | 4.5 KB | 496 |
| `parts.csv.gz` (not used) | 1.06 MB | 64,946 |

- **The index's size:** the sets, minifigures and theme tree as compact JSON arrays are about **2.5 MB, and 640 KB gzipped**. This was measured with a throwaway script on those files, not with the builder Issue A writes.
- **Images:** 2,669 of the 28,565 sets have a stock image whose name isn't `<set number>.jpg`. Every minifigure's is `<fig number>.jpg`. So the index stores an image path only for the sets that differ (`[CAT-6]`).
- **The files carry an `ETag` and a `Last-Modified`.** All four were last modified on the morning of 2026-11-02, UTC.

**Four traps the clauses close:**
- **A broken download must not replace a good index.** A truncated file parses as a short one. A build that shrinks by more than 10% writes nothing, and the previous index stays (`[CAT-7]`).
- **The device must never be left without an index.** It replaces the stored one only after the new one is fully read (`[CAT-10]`).
- **The index must not become a way into `lego_set`.** The phone sends a set number, never catalogue fields. The server fills `lego_set` from its own lookup when the item syncs, as today (`[ITEM-4]`, `[CAT-11]`).
- **Rebrickable's minifigure numbers are not BrickLink's.** Rebrickable's are `fig-000001`, and BrickLink prices a minifigure by its reference number (`[VAL-2]`). So a picked minifigure fills the name only (`[CAT-11]`).

## 2. Scope

**This project is:**
- the builder: a function that downloads the three files, builds the index and writes it to the private photo bucket, once a week;
- `GET /admin/api/sets/index`, which serves it to the signed-in admin;
- the entry form: the index kept on the device, searched there, online and offline, with Rebrickable's live search as the fallback;
- the index's age on `/admin`, the log events, and their rows in `docs/observability.md`.

**It is not:**
- **The parts list.** Nothing in the app types a part number by hand: the parts come from the owner's file, with their names (`[PARTS-3]`). Rebrickable's part numbers also differ from BrickLink's in places. A feature that adds a parts lot by hand would bring it back, as its own item.
- **The full inventories.** They are over a million rows.
- **A theme filter.** The index keeps every theme's parent, so a later overview filter can group sets by their top-level theme (`Star Wars` for `Ultimate Collector Series`). This project stores no top-level theme in `lego_set` and adds no filter.
- **The collectible-minifigure table** of `src/server/valuation/values.ts` (#248). The index could later help build it, since `sets.csv` lists each series. It is hand-made, and stays so here.
- **A change to `searchSets` on the server.** It stays the fallback, as it is.
- **A schema change or a migration.**

## 3. Decomposition

### Issue A — Build the set index weekly from Rebrickable's downloads, and serve it to the admin
**Milestone:** Product Backlog · **Labels:** `enhancement`

This item builds:
- **`src/server/catalogue/set-index/`:**
  - `buildSetIndex`, which downloads the three files, parses them, checks them against the previous index and writes the new one (`[CAT-6]`, `[CAT-7]`);
  - a small RFC 4180 parser, tested on its own with quoted commas and quotes. Names such as `"Sticker Sheet for Sets 618-1, 628-2"` hold both. It adds no dependency;
  - the worker's handler, which calls `buildSetIndex` and logs the outcome;
  - `setIndexFile(admin, { ifNoneMatch })`, an `adminOperation` that reads the current index from S3.
- **The index:** a versioned file under `set-index/`, named by its content hash, and a small `current` pointer that names it. The previous version is kept until the next build replaces it.
- **The route:** `GET /admin/api/sets/index`, added to the route test that refuses an anonymous request (`[CAT-9]`).
- **`infra/set-index.ts`:**
  - the builder: a Node 24 arm64 function with 512 MB and a 2-minute timeout, and no retries. It is linked to no database and no secret. It may write, read and delete under `set-index/` of the photo bucket alone;
  - a weekly schedule, on Monday at 08:00 UTC, after Rebrickable's morning refresh (`[CAT-8]`);
  - the admin's role may read under `set-index/`.
- **`docs/observability.md`:** rows for `set_index.built` and `set_index.build.failed` in the not-paged table.
- **`docs/deploy.md`:** how to run the builder once by hand after the first deploy, so the form has an index before the first Monday.
- **`docs/security-review.md`:** a dated pass, because this adds infrastructure, a scheduled function that reads the internet, and an admin route.

The files' columns and keys are in Rebrickable's schema diagram, <https://rebrickable.com/static/img/diagrams/downloads_schema_v4.svg>; the builder reads `sets`, `minifigs` and `themes` only. Rebrickable's downloads page allows this use (decision 1): the builder fetches only the archive files, never a Rebrickable web page, and at most once a day.

## 4. Cost

**About $0.01 a month or less, and $0 inside the free tiers.** The Owner approved a weekly rebuild. This is its estimate under `AGENTS.md` §3, at Frankfurt prices:
- **How often:** once a week, about 4.3 runs a month, each about 15 seconds.
- **Aurora: never woken.** The builder is linked to no database. The phone's check is an admin request, made only when the owner opens the admin, as any admin page is.
- **Lambda:** 512 MB for 15 seconds is 7.5 GB-seconds a run, about 33 a month. That is inside the free tier, and about $0.0005 at list price.
- **The schedule:** an EventBridge schedule. Scheduled invocations at this rate are free.
- **S3 storage:** two versions of about 640 KB, about 1.3 MB, about $0.00003.
- **S3 requests:** about 20 writes and a few hundred reads a month, about $0.0002.
- **Transfer:** the phone downloads about 640 KB a week per device, through the admin's CloudFront distribution. Two devices make about 6 MB a month, inside the free tier, and about $0.0005 at list price. Downloads from Rebrickable's CDN are inbound, and free.
- **Logs:** two lines a week.
- **No alarm, no NAT, no new bucket, no new distribution.**

## 5. Observability

- **Add, not paged:** `set_index.built`, with the counts, the skipped rows, the size and the version. It records the schedule working.
- **Add, not paged:** `set_index.build.failed`, with the stage (`download`, `parse`, `check` or `write`) and the reason.
- **No alarm.** A failed build leaves the previous index working on every device. Search still answers, and a set newer than the index still comes from Rebrickable's live search. The owner sees the index's age on `/admin`, which says when it is older than 14 days (`[CAT-10]`), so two failed weeks in a row show up without a page. An alarm on the builder's errors would cost about $0.10 a month for a failure that degrades nothing at once.
- **What would change the answer:** the live search being removed, or the index becoming the only source for a lookup.

## 6. Blast radius — what will need a human

- **Issue A:** `infra/` (`infra`), for the builder, its schedule and its permissions, and the admin's read permission on the photo bucket. It needs the dated security pass. The photo bucket's description in `infra/photos.ts` gains the `set-index/` prefix.
  - **`src/server/photos/`** (`other`) is not touched: the index is written by its own module.
  - **Public and private:** the index holds only Rebrickable's public facts, and the builder can't reach the database (`[CAT-6]`). `[PUB-1]` and the snapshot distribution are unchanged.
- **Issue B:** no escalation path. `src/app/_offline/` and the service worker are outside `docs/qa/escalation-paths.md`. The service worker needs no change: the index is an admin route's answer, which it already never caches (`[SYNC-6]`).
- **No CSP change.** The admin sends no Content-Security-Policy today (`git grep -n "Content-Security-Policy" -- next.config.ts src/app` finds nothing), and the index comes from the admin's own origin.
- **No schema change and no migration.**
- **The first deploy** creates the builder. Until it first runs, the route answers 404 and the form searches as it does today.

## 7. Decisions

Answered by `@yedeya`, as Owner, on 2026-11-03:

1. **The source. ✅ Rebrickable's free daily downloads,** not BrickLink. BrickLink has no bulk export in its API, and scraping it is against its terms. Rebrickable's downloads page, as the Owner read it on 2026-11-03: "You may automate downloading these archives at most once a day. Scraping our web pages is strictly against our Terms and will get you banned." A weekly build, plus the rare run by hand, stays within that. The page states no attribution rule.
2. **The index. ✅ Sets and minifigures, built by a small function and stored in S3.**
3. **On the phone. ✅ Kept on the device and searched there,** downloaded only when it changed, with Rebrickable's live search as the fallback.
4. **The schedule. ✅ A weekly rebuild,** which never touches Aurora, at about $0.01 a month or less.
5. **The parts list and the full inventories. ✅ The parts list is optional, and the inventories are out.** The Lead leaves the parts list out of this project (§2).
6. **The Lead's technical choices, under 1 to 5:**
   - **Served behind the admin, not at a public path.** The index holds nothing private, but a public path would add a second kind of object to the snapshot distribution, a cache behaviour, CORS for the admin's origin and a bucket policy statement, all beside `[PUB-1]`'s boundary. Behind the admin it needs none of these, and the public catalogue can't link to what it can't reach. A presigned S3 URL was also rejected: it needs a CORS rule for GET on the photo bucket;
   - **the photo bucket,** under its own prefix, rather than a new bucket. It is already private and unserved. The snapshot bucket was rejected because it is the public catalogue's;
   - a version named by the content hash, so the phone's check is one conditional request;
   - a refused build below 90% of the previous index's rows;
   - logout deletes the index, so a signed-out device holds nothing the admin put there;
   - stale after 14 days, two missed weekly builds;
   - no image URL from the index in `lego_set`. The image still comes from the lookup when the item syncs.

## 8. What I did not examine

- **The size measurement** used a throwaway script with JSON arrays, not the format Issue A will pick. A different shape changes the 640 KB by tens of percent, not by a factor.
- **A binary answer through OpenNext and CloudFront** is not tested. The route answers about 640 KB of gzip with a `Content-Type` that no layer compresses again, and the client decompresses it with `DecompressionStream`. Issue A checks that the bytes arrive intact on the deployed admin.
- **Search speed on a phone** over about 46,000 rows is inferred, not measured. A linear scan of that size takes a few milliseconds on a recent phone. Issue B measures it on the reference phone and says so in its PR.
- **IndexedDB's quota on iOS** for a 2.5 MB value is recalled as ample. The queue already asks for persistent storage (`[SYNC-7]`).
- **Whether `sets.csv` changes daily** is inferred from one day's `Last-Modified`. It doesn't matter to the cost: an unchanged index is not written again.
