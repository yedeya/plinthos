# Project brief — Walking skeleton: the deployable architecture, production only

The mandate is [#6](https://github.com/yedeya/plinthos/issues/6)'s body (`K-PROJ-15`). The architecture is `AGENTS.md`'s, which supersedes `HANDOVER.md` §7. This brief plans the thinnest slice of it that deploys, with no catalogue feature, and seeds the spec layer that slice is held to: seven new areas under `docs/qa/specs/`, `DEV`, `PLAT`, `AUTH`, `PUB`, `OPS`, `SYNC` and `PHOTO`, 61 clauses, every one `[seed]`. The slice includes the offline architecture, because the Maintainer put offline entry in the skeleton (decision 2).

## 1. The real problem

**One root cause: nothing exists yet.** The mandate's items are not separate defects but the parts of one first deployment, and they are planned as one dependency chain rather than as point fixes. Each of these re-runs on `main`:

- **No code.** `git ls-files ':!docs/' ':!.github/' ':!*.md'` prints only `.claude/settings.json`.
- **No gates.** `git grep -n "None yet" -- docs/qa/stack.md` shows `## Gates` is empty, and `ci.yml` runs only Kanon's lane check (`git grep -n "uses:" -- .github/workflows/ci.yml`).
- **A test database is declared that nothing starts.** `git grep -n "Test database" -- docs/qa/test-database.md` declares `hook`, while `git grep -n "No project setup yet" -- .github/actions/project-setup/action.yml` shows the hook only echoes. A lane that asks for a database gets no `DATABASE_URL` today (inferred from `K-LAYOUT-16`, not observed in a run).
- **No spec layer.** `git ls-files docs/qa/specs` was empty, so `kanon-spec-coverage` crashed on the missing locked set. This brief adds the corpus, an empty registry and an empty locked set.

Three governance gaps would each stop or weaken the pipeline on their own, so they are planned in, not left as findings:

- **No escalation paths.** `git ls-files docs/qa/escalation-paths.md` prints nothing, so Kanon's default applies and only `.github/`, `docs/qa/` and the agent instructions escalate (`K-LAYOUT-8`; `kanon-spec-coverage` says so on every run). As things stand the Merger could merge the login, the IAM role or a migration without the Owner. Issue A writes the file before any such code exists (`[DEV-6]`, decision 7).
- **No reference environment.** `git grep -n "^## Deploy" -- docs/qa/adoption.md` prints nothing, so no project here can close (`K-PROJ-11`). Issue B declares `production` as the reference environment (decision 6).
- **No observability document.** `git ls-files docs/observability.md` prints nothing. Issue C starts it with the anchored tables (`[OPS-3]`).

**One more gap would have stopped this very brief, and it is Kanon's, not this project's.** At the release pinned here, `kanon-brief-guard` crashed before it checked anything, with `App register docs/qa/agent-identities.md lists no Releaser App`. The guard imports `lead-reconcile.mjs`, which imports `dispatch-sweep.mjs`, and that module looks up the Releaser's login when it loads. By the same import, the reconciler tick that files this brief's issues would have crashed too (inferred from the code). The Owner has since created the Releaser App and committed its row on this branch (`70070b0`, decision 17), and `kanon-brief-guard` now runs to completion. The crash is reported to Kanon as an upstream finding.

**Three design traps the clauses close by construction. The first two would quietly defeat the cost target, and the third the privacy rule:**

- **Anonymous traffic must not wake Aurora.** A login form or an admin route that queries the database on an anonymous request lets any bot keep a 0-ACU cluster awake, which costs about $51 a month at 0.5 ACU (§4). So the password is checked against configuration without the database, a forged cookie is refused on its signature alone, and the rate limiter lives outside Aurora (`[AUTH-2]`, `[AUTH-6]`, `[AUTH-12]`). The cluster wakes only for a valid session, a migration or a publish.
- **Middleware alone is not an authorization check.** Next.js middleware has been bypassed with a forged `x-middleware-subrequest` header (recalled, CVE-2025-29927, not re-verified). So the check runs in each route's server code and in every service function that changes data, and the route test sends that header on an anonymous request (`[AUTH-3]`, `[AUTH-5]`).
- **An offline cache must not hold private data outside the session.** A service worker that caches what an admin page returned keeps private fields in the phone's Cache Storage, where logout and session expiry don't reach. A queue that uploads photos as they arrived would store their GPS. So the service worker caches only the shell and the static assets, logout clears the queue and the caches, and the server re-encodes every photo without ever writing the uploaded bytes (`[SYNC-6]`, `[SYNC-9]`, `[PHOTO-3]`, `[PHOTO-4]`).

## 2. Scope

**This project is** the walking skeleton, in one environment, `production`:

- a TypeScript workspace with typecheck, lint and test gates in CI and in `## Gates`, and a project-setup hook that installs the toolchain and a test PostgreSQL (Issue A);
- the AWS member account, the deploy role and Kanon's release and deploy lanes, set up by the Owner (Issue B);
- the SST v3 app in `eu-central-1` with one stage, its cost guards, the budget alert, the alert topic, the Next.js shell on Lambda through OpenNext with `/health/live`, `docs/observability.md` and a deploy guide someone other than its author can follow (Issue C);
- Aurora Serverless v2 at a minimum of 0 ACU behind the Data API, Drizzle with migrations, and the public/private field registry (Issue D);
- pino logging, its redaction and the failed-request path (Issue E);
- the admin login from configuration, server-revocable sessions, rate limiting, and the every-admin-route test (Issue F);
- the S3 and CloudFront path for the static snapshot, a placeholder `publishCatalogue`, and the no-private-field test (Issue G);
- the offline-sync endpoint over the typed service core, with idempotent mutations keyed by client-generated UUIDs and the `sync.conflict` event (Issue H);
- the installable admin: a web app manifest, a service worker that caches only the shell, and the IndexedDB queue that replays into the endpoint (Issue I);
- the queued photo upload: resized on the phone, re-encoded on the server, stored privately, with the GPS test (Issue J);
- a deploy rehearsal by a person other than the author, the alarm delivery and offline proofs, and the idle cost measured (Issues K and L).

**It is not:**

- **Any catalogue feature.** No set entry, parts import, Rebrickable, BrickLink or Brickset call, values or prices, settings UI, export, or catalogue page with content. The placeholder snapshot says only that nothing is published yet. These are `HANDOVER.md` §9 milestones 2 to 6.
- **Photos as a feature.** Issue J builds the upload path and nothing on top of it: a photo belongs to no set, is never published, and has no gallery, reordering or cover choice. Set entry links photos to items, and the public catalogue milestone publishes them.
- **Offline beyond the path itself.** No server-side background job, no merge of a conflict beyond retry or discard (`[SYNC-8]`), and no offline login: the admin signs in with a signal before going without one. Set entry's edits are the first mutations that can meet a version conflict in production. Until then, Issue H's tests drive the version rule with a test-only mutation (decision 19).
- **Catalogue-token rotation, the parts-download filtering of #5, or deleting `HANDOVER.md` (#4).** Rotation belongs with the public catalogue milestone, where the token is first shared. #5 and #4 depend on features this project does not build.
- **A dev or staging stage, a custom domain, a second factor, WAF, or an uptime probe.** One stage is the mandate. A domain is decision 8. WAF ($5 a month and up) and a probe (§5) fail the cost rule for a one-owner admin.
- **`docs/security-review.md`.** `AGENTS.md` §1 gates the first sharing of the catalogue link on it, and this project shares nothing. Its first pass will cover this project's auth, publish path and infrastructure.
- **A worktree script** (`AGENTS.md` §6). Separate tooling, and no item here needs two sessions at once.

**Specific to this project's definition of done:**

- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Three items are evidence, not code.** B is the Owner's setup, K a rehearsal and L a measurement. Each carries `qa:human-action`, and a human closes it with its numbers posted (`K-PROJ-9`, `K-PROJ-16`).
- **The reference environment is production**, because there is no other (`K-PROJ-11`). Verification runs the citing tests at the ref deployed there and sends no agent to production (`K-OBS-7`). Decision 6 chose Kanon's deploy lane, so the reconciler can finish the project itself.
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.

### Issue H — Add the offline-sync endpoint, with idempotent mutations and conflicts
**Milestone:** Product Backlog · **Labels:** `enhancement`
**Depends on:** Issue F (the `AdminContext` and the admin check every replayed mutation goes through)

The server half of offline entry (decision 2). The endpoint is an admin route under `src/app/admin/api/sync/`, so `[AUTH-3]`'s enumeration covers it, and the replay logic lives in `src/server/sync/`. A registry maps each mutation name to its typed service function and zod schema (`AGENTS.md` §4). The endpoint calls nothing else that changes data. An applied-mutation table records each client id with a hash of its payload and its result, in the same transaction as the change. Its first migration and schema go in `drizzle/` and `src/db/schema/`, and its columns are classified private in `[PUB-3]`'s registry. Records with a version column follow the conflict rule. No production service function has one until set entry, so the tests drive that rule with a test-only mutation (decision 19). The rows for `sync.conflict` and `sync.mutation.failed` go in `docs/observability.md`'s not-paged table (§5).

Acceptance criteria:

- `[SYNC-1]` — replay goes only through registered service functions.
- `[SYNC-2]` — idempotent by the client's id.
- `[SYNC-3]` — conflicts, and `sync.conflict`.
- `[SYNC-4]` — queue order and an outcome for each mutation.

Not in this issue: the client queue, the service worker (Issue I), photos (Issue J), or any catalogue mutation.

### Issue I — Make the admin an installable web app with an offline queue
**Milestone:** Product Backlog · **Labels:** `enhancement`
**Depends on:** Issue H (the endpoint the queue replays into)

The client half of offline entry (decision 2). The admin serves a web app manifest and registers a service worker built from `src/app/`. The worker caches the shell and the static assets, so an installed admin opens without a network. Changes made offline go into an IndexedDB queue that replays into Issue H's endpoint when the network returns and when the admin opens. Replay holds the queue across a session that ended, because a stretch offline can outlast the 7-day idle lifetime (decision 3). `/admin` shows how many mutations are pending, and lists each conflicted or failed one with retry and discard. The manifest and the worker script join `[AUTH-4]`'s public allow-list. `## Data isolation` gains `[SYNC-6]` and the test file that carries it, so a later change that lets the worker cache an authenticated response is a regression the Reviewer requests changes on. The caching rule and the logout clearing are security changes, so the Implementer stops at a plan comment first (§6).

Acceptance criteria:

- `[SYNC-5]` — installable, and opens offline.
- `[SYNC-6]` — the service worker never caches an authenticated response.
- `[SYNC-7]` — the queue survives a restart and replays.
- `[SYNC-8]` — a mutation leaves the queue only once applied.
- `[SYNC-9]` — logout warns, then clears the queue and the caches.

Not in this issue: photo uploads (Issue J), push notifications, or the Background Sync API, which Safari lacks (§8). Replay runs on the `online` event and when the admin opens.

### Issue J — Queue photo uploads and re-encode them on the server
**Milestone:** Product Backlog · **Labels:** `enhancement`
**Depends on:** Issue I (the queue an upload waits in) and Issue H (the applied-mutation record that makes an upload idempotent)

The upload route, `src/app/admin/api/photos/[id]/`, takes the bytes in the request. Under `src/server/photos/`, `registerPhoto` re-encodes them with sharp in the admin's server function into a full size and a thumbnail, as WebP with no metadata. It writes only those files to a private photo bucket, under keys the server makes. The uploaded bytes are never written to storage (`AGENTS.md` §1). This item touches:

- `infra/`, for the bucket and for the server function's memory, which sharp needs;
- `src/db/schema/` and `drizzle/`, for a `photo` table that links to no set yet, with its columns classified in `[PUB-3]`'s registry;
- `docs/deploy.md`, for the longest edge and the size cap.

`deletePhoto` is the first production mutation in Issue H's registry, so the endpoint carries a real mutation from this item on. `/admin` lists the stored photos' thumbnails through presigned URLs, each with a delete action. `## Data isolation` gains `[PHOTO-3]`, `[PHOTO-4]` and `[PHOTO-6]`, with the test files that carry them. The row for `photo.reencode.failed` goes in the not-paged table (§5). The bucket policy and the re-encoding are security changes, so the Implementer stops at a plan comment first (§6).

Acceptance criteria:

- `[PHOTO-1]` — resized on the phone, capped on the server.
- `[PHOTO-2]` — an upload is idempotent by the client's id.
- `[PHOTO-3]` — `registerPhoto` re-encodes and never stores the upload.
- `[PHOTO-4]` — no GPS or other metadata in any stored size.
- `[PHOTO-5]` — an undecodable upload stores nothing.
- `[PHOTO-6]` — random keys, a private bucket, short-lived URLs.

Not in this issue: linking a photo to a set, a gallery, reordering, a cover photo, HEIC on the server (the client's JPEG re-compression removes the need, §8), or publishing a photo.

### Issue L — Measure what the skeleton costs at rest
**Milestone:** Product Backlog · **Labels:** `enhancement` · `qa:human-action`
