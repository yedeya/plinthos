# Project brief — Walking skeleton: the deployable architecture, production only

The mandate is [#6](https://github.com/yedeya/plinthos/issues/6)'s body (`K-PROJ-15`). The architecture is `AGENTS.md`'s, which supersedes `HANDOVER.md` §7. This brief plans the thinnest slice of it that deploys, with no catalogue feature, and seeds the spec layer that slice is held to: five new areas under `docs/qa/specs/`, `DEV`, `PLAT`, `AUTH`, `PUB` and `OPS`, 46 clauses, every one `[seed]`.

## 1. The real problem

**One root cause: nothing exists yet.** The mandate's items are not separate defects but the parts of one first deployment, and they are planned as one dependency chain rather than as point fixes. Each of these re-runs on `main`:

- **No code.** `git ls-files ':!docs/' ':!.github/' ':!*.md'` prints only `.claude/settings.json`.
- **No gates.** `git grep -n "None yet" -- docs/qa/stack.md` shows `## Gates` is empty, and `ci.yml` runs only Kanon's lane check (`git grep -n "uses:" -- .github/workflows/ci.yml`).
- **A test database is declared that nothing starts.** `git grep -n "Test database" -- docs/qa/test-database.md` declares `hook`, while `git grep -n "No project setup yet" -- .github/actions/project-setup/action.yml` shows the hook only echoes. A lane that asks for a database gets no `DATABASE_URL` today (inferred from `K-LAYOUT-16`, not observed in a run).
- **No spec layer.** `git ls-files docs/qa/specs` was empty, so `kanon-spec-coverage` crashed on the missing locked set. This brief adds the corpus, an empty registry and an empty locked set.

Three governance gaps would each stop or weaken the pipeline on their own, so they are planned in, not left as findings:

- **No escalation paths.** `git ls-files docs/qa/escalation-paths.md` prints nothing, so Kanon's default applies and only `.github/`, `docs/qa/` and the agent instructions escalate (`K-LAYOUT-8`; `kanon-spec-coverage` says so on every run). As things stand the Merger could merge the login, the IAM role or a migration without the Owner. Issue A writes the file before any such code exists (`[DEV-6]`, decision 7).
- **No reference environment.** `git grep -n "^## Deploy" -- docs/qa/adoption.md` prints nothing, so no project here can close (`K-PROJ-11`). Issue B declares `production` as the reference environment (decision 6).
- **No observability document.** `git ls-files docs/observability.md` prints nothing. Issue C starts it with the anchored tables (`[OPS-3]`).

**One more gap would stop this very brief, and it is Kanon's, not this project's.** At the release pinned here, `kanon-brief-guard` crashes before it checks anything. Its error is `App register docs/qa/agent-identities.md lists no Releaser App`. The guard imports `lead-reconcile.mjs`, which imports `dispatch-sweep.mjs`, and that module looks up the Releaser's login when it loads. `git grep -n Releaser -- docs/qa/agent-identities.md` prints nothing. By the same import, the reconciler tick that files this brief's issues would crash too. That is inferred from the code. No tick here has reached that import yet: each run that `gh run list --workflow agent-lead-reconcile.yml` lists was either skipped or ended before its reconcile step. So decision 17 asks for a Releaser row before the merge, and this is reported to Kanon as an upstream finding.

**Two design traps the clauses close by construction, because each would defeat the cost target quietly:**

- **Anonymous traffic must not wake Aurora.** A login form or an admin route that queries the database on an anonymous request lets any bot keep a 0-ACU cluster awake, which costs about $51 a month at 0.5 ACU (§4). So the password is checked against configuration without the database, a forged cookie is refused on its signature alone, and the rate limiter lives outside Aurora (`[AUTH-2]`, `[AUTH-6]`, `[AUTH-12]`). The cluster wakes only for a valid session, a migration or a publish.
- **Middleware alone is not an authorization check.** Next.js middleware has been bypassed with a forged `x-middleware-subrequest` header (recalled, CVE-2025-29927, not re-verified). So the check runs in each route's server code and in every service function that changes data, and the route test sends that header (`[AUTH-3]`, `[AUTH-5]`).

## 2. Scope

**This project is** the walking skeleton, in one environment, `production`:

- a TypeScript workspace with typecheck, lint and test gates in CI and in `## Gates`, and a project-setup hook that installs the toolchain and a test PostgreSQL (Issue A);
- the AWS member account, the deploy role and Kanon's release and deploy lanes, set up by the Owner (Issue B);
- the SST v3 app in `eu-central-1` with one stage, its cost guards, the budget alert, the alert topic, `docs/observability.md` and a deploy guide someone other than its author can follow (Issue C);
- Aurora Serverless v2 at a minimum of 0 ACU behind the Data API, Drizzle with migrations, and the public/private field registry (Issue D);
- the Next.js admin on Lambda through OpenNext, `/health/live` and pino logging (Issue E);
- the admin login from configuration, server-revocable sessions, rate limiting, and the every-admin-route test (Issue F);
- the S3 and CloudFront path for the static snapshot, a placeholder `publishCatalogue`, and the no-private-field test (Issue G);
- a deploy rehearsal by a person other than the author, the alarm delivery proof, and the idle cost measured (Issues H and I).

**It is not:**

- **Any catalogue feature.** No set entry, parts import, photo upload or re-encoding, Rebrickable, BrickLink or Brickset call, values or prices, settings UI, export, or catalogue page with content. The placeholder snapshot says only that nothing is published yet. These are `HANDOVER.md` §9 milestones 2 to 6.
- **Catalogue-token rotation, the parts-download filtering of #5, or deleting `HANDOVER.md` (#4).** Rotation belongs with the public catalogue milestone, where the token is first shared. #5 and #4 depend on features this project does not build.
- **Offline queueing, a PWA manifest or a service worker.** Decision 2 asks what offline entry changes. The skeleton only takes the choice that costs nothing now, application-generated UUID keys (`[PLAT-13]`).
- **A dev or staging stage, a custom domain, a second factor, WAF, or an uptime probe.** One stage is the mandate. A domain is decision 8. WAF ($5 a month and up) and a probe (§5) fail the cost rule for a one-owner admin.
- **`docs/security-review.md`.** `AGENTS.md` §1 gates the first sharing of the catalogue link on it, and this project shares nothing. Its first pass will cover this project's auth, publish path and infrastructure.
- **A worktree script** (`AGENTS.md` §6). Separate tooling, and no item here needs two sessions at once.

**Specific to this project's definition of done:**

- **Every clause stays `[seed]`.** Promotion is a later human act (`K-SPEC-8`).
- **Three items are evidence, not code.** B is the Owner's setup, H a rehearsal and I a measurement. Each carries `qa:human-action`, and a human closes it with its numbers posted (`K-PROJ-9`, `K-PROJ-16`).
- **The reference environment is production**, because there is no other (`K-PROJ-11`). Verification runs the citing tests at the ref deployed there and sends no agent to production (`K-OBS-7`). If decision 6 picks (b), the reconciler stops at its deploy phase and the Maintainer closes the tracking issue by hand.
- **No roadmap placement.** Every item files into a bucket, so `K-PROJ-14` asks for nothing.

## 4. Cost

**One environment, so every figure is multiplied by 1.** Aurora's compute price is `AGENTS.md`'s, $0.14 per ACU-hour in Frankfurt, checked 2026-10-31. Every other price is recalled and not re-checked (§8), and Issue I measures the real figure.

| Resource | Item | Monthly |
|---|---|---|
| Alert SNS topic and its e-mail subscription | C | $0 (the first 1,000 e-mails are free) |
| AWS Budgets cost budget, no actions | C | $0 |
| VPC and subnets, with no NAT, endpoint or public IPv4 | D | $0 |
| Aurora master-credential secret, which the Data API reads | D | $0.40 |
| Aurora storage, under 1 GB | D | about $0.12 |
| Aurora compute, $0 while paused | D | about $1.10 to $1.80, below |
| Data API requests, DynamoDB on-demand rate limiter, Lambda, both CloudFront distributions, SNS | D to G | about $0, inside the always-free tiers at this volume |
| The not-paused alarm, if decision 5 pages it | D | $0.10 |
| CloudWatch Logs at 30 days, the SST state, asset and snapshot buckets | C to G | about $0.10 |

- **At rest, about $0.75 a month:** the secret, the storage, the alarm and the logs.
- **Expected while the skeleton is in use, about $2 to $3 a month.** Each deploy wakes Aurora for its migration step, about 1 minute of work plus the 5-minute pause delay at 0.5 ACU, so about $0.007. At 60 deploys a month that is about $0.42. Ten hours of admin use a month at 0.5 to 1 ACU adds $0.70 to $1.40. The maximum of 1 ACU caps an awake hour at $0.14 (decision 4).
- **What this project adds as a recurring schedule: none.** `[PLAT-7]` keeps it so. The smoke check probes only `/health/live`, which never touches Aurora (`[PLAT-14]`), and CI tests run against the hook's local PostgreSQL.
- **The failure the guards exist for.** A cluster that never pauses costs 0.5 ACU × 730 hours × $0.14, about $51.10 a month. `[AUTH-6]` removes the anonymous path that could cause it. `[OPS-7]` pages within 12 hours, and the budget (`[PLAT-6]`) pages on its forecast.
- **What is deliberately not bought:** a NAT gateway (about $41.60), a public IPv4 address (about $3.65 each), a VPC interface endpoint (several dollars per AZ), a customer-managed KMS key ($1), WAF ($5 and up), a Route 53 zone ($0.50, decision 8), and a synthetic canary (about $10 at a 5-minute cadence). `[PLAT-5]` refuses the first four in code.
- **Optional, only if decision 5 adds them:** a paged `admin.request.failed` or `catalogue.publish.failed` costs about $0.40 each, a metric filter's custom metric plus its alarm.

**Agent and CI spend.** The lanes run on the subscription token (`git grep -n CLAUDE_CODE_OAUTH_TOKEN -- .github/workflows/agent-implement.yml`), so the six pull-request items, A and C to G, draw quota rather than dollars. Each run is capped by Kanon's Implementer ceiling, $120 at the release pinned here. Actions minutes are free on this public repository.

## 5. Observability

**Add:**

- `docs/observability.md`, with the paged, not-paged and hand-created tables `K-LAYOUT-5` anchors, held to the code by a parity test (`[OPS-3]`, Issue C);
- one SNS alert topic with the owner's e-mail from configuration (`[OPS-4]`);
- **paged:** the budget at 80% of actual and 100% of forecast (`[PLAT-6]`), and the CloudWatch alarm on Aurora not pausing for 12 hours (`[OPS-7]`). Both protect the cost target, nothing else sees either in time, and each has one action: find what keeps the cluster awake. The 12-hour threshold is not measured yet. Issue I's data is what would move it (`K-OBS-4`, test 3);
- structured pino logging with these `businessEvent` names: `admin.request.failed`, `auth.login.succeeded`, `auth.login.failed`, `auth.login.rate_limited`, `auth.session.revoked`, `catalogue.published` and `catalogue.publish.failed` (`[OPS-1]`).

**Skip paging, recorded in the not-paged table with what would change the answer:**

- `admin.request.failed` and `catalogue.publish.failed`: every admin request and every publish is started by the one owner, who sees the failure on the page (`[OPS-5]`, `[OPS-6]`), so the admission rule's test 4 fails. A background path, such as a scheduled price refresh or the offline-sync endpoint, would change the answer.
- `auth.login.failed` and `auth.login.rate_limited`: there is no immediate human action, and the limiter already holds the line. A successful login the owner did not make would change the answer, and that is a separate signal, not added here.
- **A liveness probe:** skipped. A Route 53 health check ($0.50) or a canary (about $10) buys little for a static public path and a one-owner admin. The deploy's smoke check covers each release. Sharing the catalogue link would change the answer.
- **A failed deploy:** not a cloud alarm. The deploy lane files its own issue (`K-SHIP-8`, `K-OBS-6`).

Decision 5 asks the Owner to confirm this paging set.

## 7. Decisions

The Owner, the Maintainer and the Stakeholder are one person (`docs/qa/adoption.md`). Each headline names the role the question belongs to. `HANDOVER.md` §10's other questions (5, 6 and 8 to 12) are not asked here, because the skeleton doesn't depend on them. They belong to the feature milestones.

1. **Admin login method (`HANDOVER.md` §10.4). ⛔ OPEN — awaiting the Maintainer. Recommended: (a).** (a) A username and a password, whose scrypt hash is an SST secret, checked without the database (`[AUTH-2]`). Changing the password means setting a new hash and deploying, which ends every session (`[AUTH-10]`), and there is no in-app change form. (b) OIDC through an external identity provider, with the allowed identity in configuration. Every deployer then needs an account with that provider, there is a callback to configure, and the login depends on a third party. (c) Passkeys. Enrolment is a setup ceremony, which `AGENTS.md` §1 forbids unless it is bootstrapped from configuration, so they are later work. A second factor is out of scope under every option.
2. **Offline entry (`HANDOVER.md` §10.7): is it needed? ⛔ OPEN — awaiting the Maintainer. Recommended: decide it before set entry, not now.** If it is needed, the architecture gains an offline-sync endpoint that calls the same service functions (`AGENTS.md` §4). It also needs idempotent mutations keyed by client-made ids, queued photo uploads through presigned S3 URLs, a `sync.conflict` signal, a service worker, and sessions long enough to outlast a stretch without signal (decision 3). The skeleton takes only the choice that costs nothing either way, application-generated UUID keys (`[PLAT-13]`, decision 16). Nothing else here changes with the answer.
3. **Session lifetimes. ⛔ OPEN — awaiting the Maintainer. Recommended: 7 days idle and 30 days absolute, both in configuration.** These feed `[AUTH-11]`. Shorter is safer on a lost phone, and longer suits offline entry. A yes to decision 2 argues for the longer end.
4. **Spend: §4's resources and estimate. ⛔ OPEN — awaiting the Owner. Recommended: approve about $0.75 a month at rest and about $2 to $3 in use, with Aurora's maximum at 1 ACU and the budget limit at $10.** This includes the one Secrets Manager secret and the DynamoDB rate-limit table. Every later resource or alarm comes back to the Owner under `AGENTS.md` §3.
5. **What pages. ⛔ OPEN — awaiting the Owner. Recommended: the budget and the Aurora not-paused alarm only, with the rest in the not-paged table as §5 lists.** The alternative is to also page `admin.request.failed` and `catalogue.publish.failed`, at about $0.40 each. §5 argues they fail test 4 while every path is owner-started. If the not-paused alarm is declined, the Lead retires `[OPS-7]` before the merge.
6. **How production is deployed, and the reference environment. ⛔ OPEN — awaiting the Owner. Recommended: (a).** (a) Kanon's release and deploy lanes (Issue B). A required reviewer on `production` holds every release, and an IAM role trusts only that environment's OIDC subject. The role holds `AdministratorAccess` in the member account, which holds nothing but Plinthos, because SST creates IAM, Lambda, CloudFront, RDS, EC2 networking, DynamoDB, SNS and Budgets resources. `production` is declared as the reference environment, so the reconciler can finish the project itself. (b) Deploy by hand only, from `docs/deploy.md`. There is then no CI credential, no reference environment and no `[PLAT-4]`. The reconciler stops at its deploy phase, and the Maintainer ends the project by hand. If (b), the Lead revises Issues B and C before the merge.
7. **Which paths escalate. ⛔ OPEN — awaiting the Owner. Recommended: the patterns below, with no `always` marker and no human-gated promotion declared, so every such change goes to the Owner.** The patterns are `^sst\.config\.ts$` and `^infra/` (`infra`), `^drizzle/` (`migrations`), `^src/db/schema/` (`schema`), `^src/server/auth/` (`auth`) and `^src/server/publish/projection` (`other`). The bail list stays Kanon's default, with no additions. Declaring `production` human-gated would let the Merger take green-zone merges on these paths (`K-MERGE-4`). That is reasonable once the clauses are confirmed, and not before.
8. **A custom domain. ⛔ OPEN — awaiting the Owner. Recommended: none in the skeleton.** The admin and the snapshot are served on their `cloudfront.net` hosts, and a domain becomes optional configuration later. A domain now costs $0.50 a month for the Route 53 zone, plus registration.
9. **Hosting, stack and photo storage (`HANDOVER.md` §10.1 to §10.3). ✅ ANSWERED (Owner, in `AGENTS.md`'s stack): AWS `eu-central-1` in its own member account, TypeScript with SST v3, Next.js, Drizzle and Aurora, and S3 behind CloudFront.** Recorded so that nobody reopens them. `HANDOVER.md` §7 is superseded, as `AGENTS.md` says.
10. **The spec areas. ✅ ANSWERED (Lead, technical): `docs/qa/specs/tooling.md` (`DEV`), `platform.md` (`PLAT`), `auth.md` (`AUTH`), `publish.md` (`PUB`) and `operations.md` (`OPS`), allocated with `kanon-spec-ids --apply`, every clause `[seed]`.** Each is named for a surface later projects extend, so set entry adds to `PUB` and `AUTH` rather than opening new areas.
11. **The toolchain. ✅ ANSWERED (Lead, technical): npm, the Node.js LTS that Lambda supports, pinned in `.nvmrc` and `engines`, strict `tsc --noEmit`, ESLint's flat config, and Vitest.** These are mainstream choices, and there is one of each (`AGENTS.md`'s constraints).
12. **The layout and the two drivers. ✅ ANSWERED (Lead, technical): `src/app/` for Next.js, `src/server/` for the typed service core, `src/db/` for the schema and the client, `drizzle/` for migrations, `infra/` for SST modules, and `tests/`. Tests use Drizzle's TCP driver against the hook's PostgreSQL, and deployed code uses its Data API driver.** The difference between the drivers (resume errors, type casts, transactions) is the one thing CI cannot see. `[PLAT-10]` names the known part, and the deploy's migration step exercises the Data API path on every release.
13. **The password hash. ✅ ANSWERED (Lead, technical): scrypt from `node:crypto`, with parameters stored beside the hash.** Argon2 needs a native module on Lambda, and scrypt is memory-hard and built in.
14. **Where the rate limiter keeps its state. ✅ ANSWERED (Lead, technical): a DynamoDB on-demand table with a TTL, priced under decision 4.** In-memory counters reset with every Lambda instance. Aurora would wake on every bot attempt, which `[AUTH-6]` forbids.
15. **Two CloudFront distributions. ✅ ANSWERED (Lead, technical): the admin's, which OpenNext creates, and the snapshot's, whose only origin is the bucket.** This way no public path can reach a Lambda, by construction (`[PUB-1]`). Distributions cost nothing at rest.
16. **Primary keys. ✅ ANSWERED (Lead, technical): UUIDs generated by the application (`[PLAT-13]`).** Changing keys after data exists is a destructive schema change, and offline entry would need client-made ids. UUIDs cost nothing now.
17. **A Releaser row in the App register, before this brief merges. ⛔ OPEN — awaiting the Owner. Recommended: create the Releaser App now and add its row to `docs/qa/agent-identities.md`, and report the crash to Kanon.** Without the row, the reconciler's filing tick crashes on load (§1), so the merge would file nothing while the project looks approved. Decision 6's release lane needs the Releaser App anyway, so creating it now only moves that step forward from Issue B. The other path is a Kanon fix that tolerates a missing Releaser, followed by a Dependabot bump. That waits on Kanon's release, and this brief must not merge before it lands.
