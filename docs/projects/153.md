# Project brief — Parts import: import the loose parts from a BrickStore or BrickLink file

The mandate is [#153](https://github.com/yedeya/plinthos/issues/153): `HANDOVER.md` §9 milestone 3, built in parallel with the public catalogue (#154) in the Owner's order of 2026-11-02 (3 and 4 now, then 5, then 6). The spec area `docs/qa/specs/parts.md` (`PARTS`, 5 clauses) is seeded here, every clause `[seed]`. Like #124, this is a compact brief, and local agents build it.

## 1. The real problem

**There are no parts.** The schema has no lot table (`git ls-files src/db/schema`), nothing parses a parts file (`git grep -il "bsx\|BrickStore" -- src/` prints nothing), and the snapshot can't show a parts summary. The Owner's loose parts, about 50,000 of them (`HANDOVER.md` §2), live in a BrickStore `.bsx` file.

**Two traps the clauses close:**
- **The file carries private data.** BrickLink sellers keep bin locations in a lot's remarks (#5). So the parser never returns a remark, a comment or any field the inventory doesn't need (`[PARTS-1]`), and the file itself is deleted after it is read (`[PARTS-2]`). A remark can't leak if it is never stored.
- **The file is XML from outside.** An XML parser that resolves entities can be made to read local files or fetch URLs. So the parser never resolves a DTD or an external entity (`[PARTS-1]`).

## 2. Scope

**This project is:**
- the `.bsx` and BrickLink XML parser;
- the upload into a private `imports/` prefix;
- `importPartsFile`, which replaces the inventory;
- `/admin/parts`, with its summary;
- the parts lot's overview photos.

**It is not:**
- **Values beyond the file's own prices.** The total value is the sum of the file's unit prices × quantities, as `HANDOVER.md` §6 asks: the Owner prices the file in BrickStore. No BrickLink call is made per lot.
- **The parts download, and per-lot data in the catalogue.** Both are #5, with the valuation milestone.
- **A lot editor or a merge** (`HANDOVER.md` §5).
- **Offline import.** A file import needs the network, because the server parses it. Overview photos can be queued offline like any photo.

## 3. Decomposition

### Issue A — Parse a BrickStore or BrickLink parts file, keeping only the inventory's fields
**Milestone:** Product Backlog · **Labels:** `enhancement`

A pure module, `src/server/parts/parse.ts`, with no schema and no route. It exports `parsePartsFile(bytes): { format: 'BSX' | 'BL_XML'; lots: PartsLot[] }`, where `PartsLot = { itemType, itemNo, colorId, condition: 'N' | 'U', quantity, unitPrice: number | null }`, and a `PartsFileRefused` error with the reason and the first lot it names. It uses an XML parser that resolves no entities, or turns them off explicitly. A test feeds it a file with an external entity and asserts that nothing is read. The fixtures are made-up files under `tests/fixtures/parts/`, in both formats. One of them has remarks holding made-up bin locations, which must not appear in the output.

Acceptance criteria:

- `[PARTS-1]`

### Issue B — Import the parts inventory, with its summary and overview photos
**Milestone:** Product Backlog · **Labels:** `enhancement`

This item builds:
- **The schema**, in one migration: a `parts_import` table and a `parts_lot` table, every column classified (`[PUB-3]`) with unit prices private. It also adds the overview photos' link: `photo.parts_lot` (a boolean) and its `position`.
- **The upload:** the presign route `src/app/admin/api/parts/uploads/`, an admin route, for a key under `imports/`. The prefix gets its lifecycle rule and its IAM permissions in `infra/photos.ts`.
- **`importPartsFile` in `src/server/parts/`:** it reads the upload with a size cap (`PLINTHOS_PARTS_MAX_BYTES`, named in `docs/deploy.md`), parses it with Issue A, replaces the lots in one transaction, and deletes the upload whatever the outcome.
- **`/admin/parts`:** the summary, the upload, the replace warning, and the overview photos, through `registerPhoto` with `partsLot: true`.
- **A parts link in the admin footer.**

The schema and `infra/` changes escalate to the Owner.

## 4. Cost

**About $0.** The `imports/` prefix lives in the existing photo bucket, and its lifecycle rule is free. An upload normally lives seconds. About 2,000 lots are a few hundred kilobytes in Aurora. A 50,000-part file may be up to a few megabytes, and parsing it once fits the server function's memory and time.

## 5. Observability

- **Add, not paged:** the `businessEvent` `parts.import.failed`, with the format, the reason and the lot it names, never the file's content or a remark. It gets a row in `docs/observability.md`'s not-paged table. The import is started by the one owner, who sees the failure on `/admin/parts` at once, as with `catalogue.publish.failed` (brief #6, §5). A server-side or scheduled import would change the answer.
- **Add, not paged:** `parts.imported`, with the number of lots and the total quantity. It records an action the owner just took.
- **No alarm.** A paged event would cost about $0.40 a month, a metric filter plus its alarm, for a failure the owner already sees.

## 6. Blast radius — what will need a human

- **Issue A:** nothing.
- **Issue B:** `src/db/schema/`, `drizzle/` and `infra/`, all additive. Brief #154's Issue A also adds a migration, so whichever merges second regenerates its own.
- **Data isolation:** unit prices are private, remarks are never stored, and `[PUB-4]`'s canary test covers the new tables.

## 8. What I did not examine

- **The `.bsx` format's exact element names.** BrickStore's documentation isn't read. The recalled shape is `<BrickStoreXML><Inventory><Item><ItemID/><ItemTypeID/><ColorID/><Condition/><Qty/><Price/><Remarks/>…`. Issue A checks BrickStore's source or documentation first, and the BrickLink XML export's `<INVENTORY><ITEM><ITEMTYPE/><ITEMID/><COLOR/><CONDITION/><QTY/><PRICE/><REMARKS/>…` too.
- **How large the Owner's real file is.** Issue B sets the cap at 20 MiB by default, and the Owner's first import measures it.
