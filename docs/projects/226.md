# Project brief — Parts prices from BrickLink: a background refresh for the loose parts inventory

The mandate is [#226](https://github.com/yedeya/plinthos/issues/226), the Owner's decisions of 2026-11-03. It changes decision 3 of #207, under which the loose parts took their value from the imported file's prices only. The brief rewrites `[VAL-3]`, `[VAL-4]` and `[VAL-6]` in `docs/qa/specs/valuation.md`, adds four clauses to it, and adjusts `[PUB-20]`. Every clause is `[seed]`. Like #207, this is a compact brief, built by local agents.

## 1. The real problem

**The parts have no market value.**
- **The value:** `[VAL-6]` sums the file's unit prices. A lot BrickStore saved without a price (`0.000`) counts for nothing, and a price from the day the file was made never moves (`src/server/valuation/values.ts`).
- **The quotes:** `price_quote` is keyed by item type, number and new or used (`src/db/schema/price-quote.ts`). A part's price depends on its colour as well, and the table's types are only `SET` and `MINIFIG`.
- **The refresh:** `refreshPrices` runs in the open page, 40 seconds per call, with the page calling again (`src/server/valuation/refresh.ts`, `src/app/_admin/values.tsx`). The inventory has thousands of lots. One call a second is an hour of pressing with the phone open.

**Three traps the clauses close:**
- **BrickLink's daily limit.** The limit is 5,000 calls a day. A full parts refresh is most of it, and a refresh that ran into it would fail every lot after that point. So the job counts its calls per UTC day, stops below the limit, and says so (`[VAL-10]`).
- **A job nobody watches.** It runs with the page closed, so a crash must not leave a run that looks busy forever, or block the next one. The run keeps a heartbeat, and a stale one reads as stopped (`[VAL-9]`).
- **No schedule.** A job that continues itself is not a schedule. It runs only from a press, and it ends when nothing is left, it is stopped, or the daily limit is reached. Nothing wakes Aurora afterwards (`AGENTS.md` §3).

## 2. Scope

**This project is:**
- price quotes per parts lot: item type, number, colour and new or used;
- one background job for every refresh, sets and minifigures included, which replaces the page's loop;
- the parts value: BrickLink first, the file's price as the fallback;
- the progress and outcome on `/admin`, and each lot's price and source on `/admin/parts`;
- the parts subtotal and the parts download's per-lot price, from the new value.

**It is not:**
- **A scheduled refresh,** nor an automatic restart the next day after the daily limit (#207, decision 2). The owner presses again.
- **BrickLink's stock prices** (current listings) as a fallback. The fallback is the file's price.
- **A price for a lot whose type BrickLink doesn't price** (`[VAL-8]`).
- **Export and the printable summary.** That is milestone 6.

## 3. Decomposition

### Issue A — Run price refreshes as a background job, with quotes per parts lot
**Milestone:** Product Backlog · **Labels:** `enhancement`

This item builds:
- **The schema, in one additive migration:**
  - a `part_price_quote` table: item type, item number, colour, new or used, average, sample size, currency, source, fetched-at, attempted-at and the last refusal, unique on the first four;
  - a `price_refresh_run` table: scope, whether it asks for every price, state, started-at, heartbeat-at, finished-at, the counts, the stop reason and a stop request;
  - a per-UTC-day count of BrickLink calls.

  Every column is classified (`[PUB-3]`). Everything in it is private.
- **The BrickLink client:** `priceGuide` takes the lot's type and colour (`[VAL-8]`).
- **`src/server/valuation/`:**
  - `startPriceRefresh(admin, { scope, all })`, which creates the run and invokes the worker;
  - `runPriceRefresh(runId, { budgetMs })`, the worker's step;
  - `stopPriceRefresh(admin)`;
  - `priceRefreshStatus(admin)`.

  `refreshPrices`'s page loop goes. The quote selection and failure rules carry over.
- **`infra/prices.ts`:** the worker, a Node 24 arm64 function with 512 MB and a 15-minute timeout and no async retries. It is linked to the database and the four BrickLink secrets, and is allowed to invoke itself and nothing else. It has no URL. The admin's server is allowed to invoke it.
- **Logs:** `price.refresh.started`, `price.refreshed` and `price.refresh.failed` (with `stalled` and `daily-limit` as reasons), with rows in `docs/observability.md`.
- **`docs/security-review.md`:** a dated pass, because this changes infrastructure.

## 4. Cost

**About $0 a month more when no refresh runs, and about $0.10 per full refresh.** This is the estimate the Owner agreed to (`AGENTS.md` §3).
- **Aurora** is awake while a run lasts. About 3,600 lots plus the sets is about an hour at one call a second, at the minimum of 0.5 ACU at $0.14 per ACU-hour: about $0.08. A partial refresh costs less, and the 7-day window keeps a second press within a week short.
- **The worker:** 512 MB for an hour is 1,800 GB-seconds, about $0.03, inside Lambda's free tier.
- **The Data API:** about four requests per lot, about 15,000 per full run, about $0.005.
- **Storage:** a few thousand quote rows, and CloudWatch Logs at one line per lot. Both are negligible.
- **No alarm, no schedule, no NAT, no fixed IP:** the keys are registered for `0.0.0.0` (#207, decision 1). Reserved concurrency is not used, because a new account's limit of 10 can't spare it. The run's lease in the database keeps two jobs from overlapping instead.

Pressing **Refresh prices** once a week would cost about $0.40 a month.

## 5. Observability

- **Add, not paged:** `price.refresh.failed`, with the reason, including `stalled` (a heartbeat older than 20 minutes in a running run) and `daily-limit`. The owner starts every run and sees its outcome on `/admin` (`[VAL-9]`, `[VAL-11]`).
- **Add, not paged:** `price.refresh.started` and `price.refreshed`, with the counts.
- **No alarm on the worker's errors.** An alarm on them would cost about $0.10 a month, for a failure `/admin` already shows as a stalled run the next time the owner looks. The job never runs unless the owner started it.

## 7. Decisions

Answered by `@yedeya`, as Owner, on 2026-11-03:

1. **Which price counts. ✅ BrickLink first.** A lot's BrickLink average counts when BrickLink has one. Otherwise the file's price counts, and otherwise there is none. `/admin` shows each lot's source.
2. **How it runs. ✅ In the background,** from a press, with the page free to close, at about $0.10 per full refresh.
3. **The Lead's technical choices, under 1 and 2:**
   - the same 6-month sold average, worldwide, in `PLINTHOS_CURRENCY`, and the same 7-day window as `[VAL-3]`;
   - one job for every refresh, so sets and minifigures leave the page loop too;
   - the file's price as the fallback only in the deployment's currency, because a total can't mix currencies. A file that names no currency is taken to be in the deployment's, as today;
   - a cap of 4,500 calls per UTC day, below BrickLink's 5,000;
   - a step of about 13 minutes per invocation, inside the 15-minute timeout;
   - a stall after 20 minutes without a heartbeat.
