# Project brief — Set entry: log sets with photos from the phone

The mandate is [#124](https://github.com/yedeya/plinthos/issues/124): the Owner needs the application as soon as possible, to start logging sets with photos. This is `HANDOVER.md` §9 milestone 2. The Owner chose a compact brief and an immediate start (decision 1). Two spec areas are seeded, `docs/qa/specs/catalogue.md` (`CAT`, 5 clauses) and `docs/qa/specs/items.md` (`ITEM`, 9 clauses), every one `[seed]`. The UI is designed in `docs/design/ui.md`.

## 1. The real problem

**One root cause: the skeleton has no item.** Sign-in, the offline queue, the sync endpoint and the photo pipeline are all on `main`, but there is nothing to attach a photo to and no screen to log a set on.

- No item table: `git ls-files src/db/schema` lists `admin-session`, `applied-mutation`, `catalogue-settings`, `classification`, `index` and `photo`.
- No catalogue lookup: `git grep -il rebrickable -- src/` prints nothing.
- The only production sync mutations are photos: `git grep -n "name: '" -- src/server/sync/mutations.ts src/server/photos/photos.ts`.
- The admin has no styling and says "There is nothing to manage yet": `git grep -n "nothing to manage" -- src/app/admin/page.tsx`.
- The version rule has never met a real record. The registry still carries `TODO(set entry)` for the racing-create conflict: `git grep -n "TODO(set entry)" -- src/server/sync/`.

## 2. Scope

**This project is:**
- a Rebrickable client and the set lookup, cached in Aurora (`CAT`);
- the item record with its photos, as offline-capable sync mutations (`ITEM-1` to `ITEM-7`);
- the item list, the one-screen entry form and the edit form, with the basic design system in `docs/design/ui.md` applied to every admin page, the sign-in and the offline shell (`ITEM-8`, `ITEM-9`).

**It is not:**
- **Values, prices or BrickLink.** That is milestone 5. No `market_value` or override column yet.
- **Items in the public catalogue.** That is milestone 4. The snapshot is unchanged, and `[PUB-4]`'s test now covers the new tables.
- **Parts import** (milestone 3), **barcode scanning** (`HANDOVER.md` §10.6: not now), or drag-to-reorder photos (decision 4 chose buttons).
- **Editing an item while offline.** Editing an existing item needs the network, because the offline shell holds no server data (`[SYNC-6]`). A new item can be logged offline (decision 2).

**Definition of done:** the Owner can log a set on the phone, offline included, with photos, and see it in the list. A deploy with `RebrickableApiKey` set is the Owner's step after the merges.

## 3. Decomposition

### Issue A — Add a rate-limited Rebrickable client and its API key
**Milestone:** Product Backlog · **Labels:** `enhancement`

A pure module under `src/server/catalogue/rebrickable.ts`, with no schema and no route. It exports:
- `CatalogueSet`: `{ setNum, name, theme, year, numParts, imageUrl }`;
- the `CatalogueProvider` interface: `searchSets(query, { budgetMs })` and `getSet(setNum, { budgetMs })`, which returns `null` for a set Rebrickable doesn't know;
- `CatalogueUnavailable`, thrown on a timeout, a refused key or exhausted retries;
- `rebrickableProvider(apiKey, { fetch })`.

Theme names resolve through Rebrickable's theme endpoint, cached in memory per instance. It also adds the `RebrickableApiKey` SST secret: `infra/config.ts` `SECRETS`, linked to the admin's server function, and named in `docs/deploy.md` step 4 with how to get a free key. Tests use a stand-in `fetch` with made-up fixtures, never the real API.

## 4. Cost

**About $0 a month more.** There are no new AWS resources. `RebrickableApiKey` is an SST secret, which costs nothing. `lego_set` and `collection_item` add kilobytes to Aurora's storage. Search runs only for a signed-in admin, and Aurora is awake for that session anyway. The Rebrickable API is free. Nothing runs on a schedule (`[PLAT-7]`).

## 5. Observability

- **Add, not paged:** the `businessEvent` `catalogue.lookup.failed`, with the reason (timeout, 429, refused key) and never the key. The owner sees the failure at once, as "search unavailable" on the form (`[CAT-5]`). A failed `saveItem` stays in the device's queue and on `/admin` (`[SYNC-8]`). That is the same reasoning as `sync.mutation.failed` in brief #6 §5. A refused key that persists would change the answer: it fails every search until the secret is fixed.
- **No new alarm.** None is worth $0.10 a month for a one-owner admin that shows the failure on the page.

## 6. Blast radius — what will need a human

- **Issue A:** `infra/config.ts` (`infra`), the secret, and the Owner's deploy with `npx sst secret set RebrickableApiKey <key> --stage production`.
- **Issue B:** `src/db/schema/` and `drizzle/`, a new migration. It is additive only, under the expand-first rule (`docs/qa/stack.md` `## Schema changes`): the new tables, and nullable new columns on `photo`. This deploy ships the migration and the code that reads it together, the window #78 describes, for one deploy and only for the owner. It is accepted for speed (decision 1), and the migration step runs straight after `sst deploy`.
- **Issue C:** `src/app/` only.
- **Data isolation:** `storage_location` is private. `[PUB-3]` and `[PUB-4]` cover the new tables in B's change.
