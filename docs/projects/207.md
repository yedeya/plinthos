# Project brief — Valuation and selling mode: BrickLink values, overrides, and the catalogue as an offer

The mandate is [#207](https://github.com/yedeya/plinthos/issues/207): `HANDOVER.md` §9 milestone 5, with selling mode in the same milestone (the Owner's decisions of 2026-11-03). The brief seeds a new spec area, `docs/qa/specs/valuation.md` (`VAL`, 7 clauses), and adds four selling-mode clauses to `docs/qa/specs/publish.md` (`PUB-17` to `PUB-20`). Every clause is `[seed]`. Like #124, #153 and #154, this is a compact brief, built by local agents.

## 1. The real problem

**Nothing has a value.**
- **The schema:** it has no price table (`git ls-files src/db/schema`). `catalogue_settings` holds `show_values`, `selling_mode` and `selling_value_display`, which nothing reads or sets (`git grep -n "showValues\|sellingMode" -- src/server src/app`).
- **The projection:** it publishes no value, and its module comment says the first content item to publish a value reads those settings (`src/server/publish/projection.ts`).
- **The parts value:** the imported parts carry their file's prices (`parts_lot.unit_price`, `parts_import.total_value`), and nothing shows them.

**Three traps the clauses close:**
- **A hidden value must not leak through an aggregate** (`AGENTS.md` §1). Totals, subtotals and a sort by value are published only when a value they come from is shown (`[PUB-17]`, `[PUB-18]`). `[PUB-4]`'s canary test already runs under every combination of the three settings, and it gains the new fields: the asking prices, the overrides and the quotes.
- **A refresh must fit the server function and BrickLink's limit.** About 150 items at one request a second is more than one 55-second invocation. So `refreshPrices` does what fits its budget and answers what is left, and the page calls it again (`[VAL-3]`). Nothing runs on a schedule, so Aurora wakes only when the owner presses the button (`AGENTS.md` §3).
- **The parts download must not carry the bin locations** (#5). It is generated from the stored lots, which never held a remark (`[PARTS-1]`), and per-lot prices appear only when market values are shown (`[PUB-20]`).

## 2. Scope

**This project is:**
- the BrickLink client;
- price quotes for sets and numbered minifigures, refreshed on demand;
- values, with manual overrides and per-condition adjustments;
- the admin's values and totals;
- **Show values** in the catalogue;
- selling mode: the value display, asking prices, split views and the parts download.

**It is not:**
- **A scheduled refresh** (the Owner's decision 2).
- **BrickEconomy** (`HANDOVER.md` §10.5: BrickLink).
- **A price per parts lot from BrickLink** (`HANDOVER.md` §6: the file's own prices).
- **Selling itself,** that is checkout, listings or sync with BrickLink stores (`HANDOVER.md` §5).
- **Export and the printable summary.** That is milestone 6.

## 3. Decomposition

### Issue A — Add a signed, rate-limited BrickLink price-guide client and its secrets
**Milestone:** Product Backlog · **Labels:** `enhancement`

A pure module, `src/server/valuation/bricklink.ts`, with no schema and no route. It exports:
- `PriceGuide = { itemType: 'SET' | 'MINIFIG'; itemNo: string; newOrUsed: 'N' | 'U'; average: number | null; sampleSize: number; currency: string }`;
- `PriceProvider`, with `priceGuide(itemType, itemNo, newOrUsed, { budgetMs }) → PriceGuide | null`, where null means BrickLink doesn't know the item;
- `PriceUnavailable` (`reason`: `timeout`, `rate-limited`, `refused-key` or `upstream`);
- `bricklinkProvider(credentials, { fetch, now, sleep })`;
- `linkedPriceProvider()`.

The client signs OAuth 1.0a with HMAC-SHA1 from `node:crypto`, with no dependency unless one is clearly better. It also adds the four secrets to `infra/config.ts` `SECRETS`, linked to the admin's server function, and to `docs/deploy.md` step 4, and adds `PLINTHOS_CURRENCY` (default `EUR`) to the configuration. Tests use a stand-in `fetch` and check the OAuth signature against a published worked example.

### Issue B — Store prices and values, with an on-demand refresh, overrides and adjustments
**Milestone:** Product Backlog · **Labels:** `enhancement`

This item builds:
- **The schema, in one additive migration:**
  - a `price_quote` table: item type, item number, new or used, average, sample size, currency, source, a fetched-at time, and the last refusal;
  - `collection_item.manual_value_override` and its currency;
  - `catalogue_settings` adjustment percentages for `USED_WITH_BOX` and `USED_NO_BOX`.

  Every column is classified (`[PUB-3]`). Values, quotes, overrides and adjustments are private.
- **`src/server/valuation/`:**
  - `refreshPrices(admin, { all? })`, budgeted, oldest first, answering `{ done, left, failed }`;

- **`/admin`:**
  - the **Refresh prices** button, with progress, calling again until nothing is left;
  - each item's value with its source and date;
  - totals per segment.
- **The edit form:** the override.
- **`/admin/settings`:** the two adjustments.

It builds against Issue A's interface and merges after it.

## 4. Cost

**About $0 a month more.**
- The four BrickLink secrets are SST secrets, which cost nothing.
- `price_quote` adds a few hundred rows to Aurora's storage.
- A refresh runs only when the owner presses the button. It wakes Aurora for a few minutes, about the same as one publish: around $0.01 a press.
- The parts download adds two small files to each snapshot.
- There is no schedule, no alarm and no new resource (`AGENTS.md` §3).

## 5. Observability

- **Add, not paged:** `price.refresh.failed`, with the reason, never a secret, and a row in `docs/observability.md`'s not-paged table. The owner starts every refresh and sees its outcome on `/admin` (`[VAL-4]`). A scheduled refresh would change the answer, and decision 2 has none.
- **Add, not paged:** `price.refreshed`, with the counts. It records an action the owner just took.
- **No alarm.** Paging either event would cost about $0.40 a month, for a failure the owner already sees.

## 6. Blast radius — what will need a human

- **Issue A:** `infra/config.ts` (`infra`) for the secrets and the currency.
- **Issue B:** `src/db/schema/` and `drizzle/`. The migration is additive, and its new columns are nullable or defaulted, so it can run before the deploy, as #204's did.
- **Issue C:** `src/server/publish/projection.ts` (`other`), `src/db/schema/` and `drizzle/`, plus the dated security pass. `[PUB-4]` is held in `## Data isolation`, and every new field passes it.
- **Migrations:** B's and C's are separate. Whichever merges second regenerates its own.

## 7. Decisions

Answered by `@yedeya`, as Owner, on 2026-11-03:

1. **BrickLink access. ✅ The keys are registered with IP `0.0.0.0`, and set as the four SST secrets.** No fixed-IP fallback is needed (`AGENTS.md` §3).
2. **Refresh. ✅ On demand only:** a button on `/admin`, with no schedule.
3. **What is valued from BrickLink. ✅ Sets, by condition, and minifigures with a reference number.** Loose parts take their value from the BrickStore file's prices. Bulk lots and other items have only a manual override.
4. **Selling mode. ✅ In this milestone,** with every switch off by default.
5. **The Lead's technical choices, under 1 to 4:**
   - the 6-month sold average, worldwide, in `PLINTHOS_CURRENCY`;
   - a 7-day freshness window before a quote is fetched again;
   - `ASKING` as the display default (`HANDOVER.md` §10.9);
   - adjustments that default to 0 % (`HANDOVER.md` §10.8).
