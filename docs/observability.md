# Observability

The one home for what each of Plinthos's signals means (`AGENTS.md` §2, `K-OBS-2`). `sst.config.ts` and `infra/` say what notifies; this document says what each notification means and what to do about it. Change both in the same pull request: `tests/infra/observability.test.ts` fails when a budget notification or an alarm the stack defines has no paged row here, when a paged row has no notification behind it, and when a `businessEvent` the code emits is in neither or both of the paged and not-paged tables (`[OPS-3]`).

Every paged signal goes to one SNS topic, `Alerts` (`infra/alerts.ts`), which e-mails the address in the `AlertEmail` secret (`[OPS-4]`). Whether a signal pages is decided by Kanon's admission rule, `K-OBS-4`; each decision not to page is a row of the not-paged table, with what would change it (`K-OBS-3`).

## Paged signals

These protect the cost target, under $10 a month (`AGENTS.md` §3). The limit is the deployment's `PLINTHOS_BUDGET_LIMIT_USD`, $10 unless it sets another (`docs/deploy.md`). AWS Budgets charges nothing for the budget and SNS nothing for these e-mails, so neither row adds to the bill. The not-paused alarm is a CloudWatch alarm, about $0.10 a month, which the Owner approved (`docs/projects/6.md`, decisions 4 and 5).

<!-- paging-clauses:table -->

| Signal | What it means | Threshold | What a person does |
|---|---|---|---|
| `budget.actual.80` | This month's actual spend on the account has passed 80% of the budget limit (`[PLAT-6]`). | Actual cost above 80% of the limit, as AWS Budgets measures it, a few times a day. | Open Cost Explorer for the month, grouped by service, and find what grew. The usual cause is an Aurora cluster that never pauses: find what keeps it awake. |
| `budget.forecast.100` | AWS forecasts that this month's spend will pass the budget limit (`[PLAT-6]`). | Forecast cost above 100% of the limit. | The same as above, before the money is spent: find the service whose daily cost grew, and stop what drives it. |
| `aurora.not_paused` | The Aurora cluster has stayed awake for 12 hours without pausing once (`[OPS-7]`, `infra/database.ts`). Awake all month at 0.5 ACU it would cost about $51, five times the budget. A recovery e-mail follows when it pauses again. | `ServerlessDatabaseCapacity`'s minimum above 0 in each of 12 consecutive one-hour periods; an hour with no data does not count. The 12 hours are not measured yet: #24's figures could move them. | Find what keeps calling the database. Something reaching it at least every five minutes keeps it awake: a schedule, a client retrying, or an anonymous path that touches the database (`[PLAT-7]`, `[AUTH-6]`). The cluster's CloudWatch metrics and the admin's logs show when the calls come. |

## Not-paged signals

<!-- not-paged-table -->

| Signal | Why it does not page | What would change the answer |
|---|---|---|
| `health.live` | There is no uptime probe. A Route 53 health check (about $0.50 a month) or a canary (about $10 at a 5-minute cadence) buys little for a one-owner admin, and the deploy's smoke check probes `/health/live` on every release (`[PLAT-4]`), without waking the database (`[PLAT-14]`). | Sharing the catalogue link with buyers, whose visits nobody else would see fail. |
| `admin.request.failed` | The admin's server code failed a request (`src/server/request-failure.ts`, `[OPS-5]`). Each request has its own id, a UUID the admin wrappers make (`src/server/auth/admin.ts`). Every admin request is started by the one owner, who sees the failure on the page, with the request id that the error line in the server function's log group names, so nobody needs paging (brief #6, §5 and decision 5). Paging it would cost about $0.40 a month, a metric filter's custom metric and its alarm. | A server-side background path, such as a scheduled price refresh, whose failures no one would see on a page. |
| `auth.login.succeeded` | The admin signed in (`src/server/auth/sign-in.ts`). It records an action the owner just took, so there is nothing to act on (brief #6, §5 and decision 5). | A sign-in the owner did not make, which would need its own signal, such as a notice on each new session: not added here. |
| `auth.login.failed` | A sign-in attempt had the wrong username or password, or neither. It never reaches the database (`[AUTH-6]`), and the rate limit already holds the line (`[AUTH-12]`), so there is no immediate human action (brief #6, §5). | A run of failures that suggests a targeted guess at the password, if the owner wants to be told; or a successful sign-in the owner did not make. |
| `auth.login.rate_limited` | An attempt was refused because an address, or all of them together, passed the sign-in's limit (`[AUTH-12]`). The limiter is already the response, and paging would cost an alarm, about $0.40 a month with its metric filter (brief #6, §5). | The owner finding themselves locked out by someone else's attempts, which the total limit can cause when many addresses try at once (one address alone can't, `[AUTH-13]`): then a per-address allow-list or a page would be worth its cost. Until then, raising `PLINTHOS_LOGIN_ATTEMPTS_TOTAL` and deploying again lets the owner back in (`docs/deploy.md`, step 3). |
| `auth.login.not_via_cloudfront` | A request reached `POST /auth/login` through the server function's own URL rather than the admin's CloudFront distribution, and was refused with 403 before anything else (`[AUTH-14]`, `src/server/auth/via-cloudfront.ts`). A browser never sends one: only a caller that found the URL and is trying to choose the address the rate limiter counts it under. The refusal is the response. It never reaches the rate limiter or the database, and paging would cost an alarm, about $0.40 a month with its metric filter (#61). | A run of them that shows someone probing the URL, if the owner wants to be told; or the owner's own sign-in being refused, which would mean the distribution no longer sets the header, and which the owner sees at once on the login page. |
| `auth.session.revoked` | The admin signed out, and the session was deleted on the server (`[AUTH-9]`). It records an action the owner just took (brief #6, §5). | A revocation the owner did not make. |
| `auth.sessions.revoked_on_rotation` | The deploy's migration step deleted the sessions signed with a key other than the deployed one, and `revoked` says how many (`src/server/auth/sessions.ts`, `[AUTH-10]`). It runs on every deploy, and finds none unless `AdminUsername`, `AdminPasswordHash` or `SessionSecret` changed: then it is the owner's own change taking effect, which is expected, not a failure (#60). A sweep that fails fails the deploy, which the deploy lane already reports (`deploy.failed`). | Sessions revoked at a deploy that changed no credential, which would mean the key's derivation changed. |
| `sync.conflict` | An offline mutation the admin's device replayed was not applied: its id was applied before with another payload, or the record it changes has moved past the version it was made against (`src/server/sync/replay.ts`, `[SYNC-3]`). The line names the mutation's id, its service function and the reason, never its payload. A replay runs from the owner's own device, often with no page in front of them, but the conflict is not lost: the mutation stays in the device's queue and is listed on `/admin` until the owner retries or discards it (`[SYNC-8]`), and nothing on the server could act sooner (brief #6, §5 and decision 5). Paging it would cost about $0.40 a month. | A client that drops a conflicted mutation, or a replay that runs on the server rather than from the device. |
| `sync.mutation.failed` | An offline mutation failed on the server and was rolled back, its change and its applied record together (`src/server/sync/replay.ts`, `[SYNC-4]`). The error line names the mutation's id, its service function, the request id the response gave the device, and the failure's innermost cause, never the payload. The device keeps the mutation in its place in the queue and retries it by itself, at its next open or reconnect after a backoff, up to `MAX_FAILED_ATTEMPTS` failures (`src/app/_offline/replay.ts`); then it holds it on `/admin` until the owner retries or discards it (`[SYNC-8]`). So several lines for one mutation id, each with its own request id, are those retries, not separate failures. Paging it would cost about $0.40 a month. | A client that drops a failed mutation, or a replay that runs on the server rather than from the device. |
| `sync.mutation.settle_failed` | What an offline mutation does outside the database once its transaction has ended failed (`src/server/sync/replay.ts`, the registry's `settled`). The mutation's outcome stands; the line names its id, its service function and the failure's innermost cause. Today only `registerPhoto` has such a step, which catches its own failures as `photo.cleanup.failed`, so this line means a bug in that step. Nothing is lost: a quarantined upload expires within about a day (`[PHOTO-7]`). | A step whose failure loses data or leaves something served, which would need a page. |
| `sync.batch.out_of_time` | An offline-sync batch reached the point where its next mutation's worst case no longer fit in `BATCH_BUDGET_MS`, so that mutation and every one after it were answered as not attempted (`src/server/sync/replay.ts`, `[SYNC-11]`). The info line names the first mutation not attempted, its service function and how many were left, never a payload. Nothing failed and nothing is lost: the device sends the rest at once in its next batch, so the owner sees one sync that took two requests. It is the bound working, as a batch of many new sets or a slow database makes it work (#138). Paging it would cost about $0.40 a month. | Lines for most batches, which would mean the estimates in `src/server/sync/limits.ts` are too long, or the database is slow enough to look at. |
| `transaction.after_commit.failed` | A step a service function registered with `afterCommit` threw after its transaction had committed (`src/server/transaction.ts`). The commit stands and the steps after it still run; the line names the error's kind, never its message. Today the only such step is `deletePhoto`'s file deletion, which catches and logs its own failures as `photo.cleanup.failed`, so this line means a bug in a step that forgot to. | A step whose failure loses data or leaves something served, which would need a page. |
| `photo.reencode.failed` | A photo the phone uploaded was refused and stored nothing (`src/server/photos/photos.ts`, `[PHOTO-5]`): over the size cap, bytes that don't match the hash the phone recorded, not a JPEG the server can decode, or a failure on the server. The line names the mutation's id, the reason and the request id, never the bytes. Its quarantined upload is deleted all the same. The photo stays in the phone's queue with its bytes (`[PHOTO-8]`, #9). With the reason `failed`, the phone first retries it by itself, at its next open or reconnect after a backoff, up to `MAX_FAILED_ATTEMPTS` failures, uploading it again since its upload was deleted; then, as with every other reason at once, it is held on `/admin` until the owner retries or discards it (`[SYNC-8]`), so the owner meets it the next time they open the admin, and nothing on the server could act sooner (brief #6, §5 and decision 5). Paging it would cost about $0.40 a month. | A client that drops a refused photo, or a re-encode that runs on the server rather than in the owner's own replay. |
| `photo.cleanup.failed` | A file the photo path deletes could not be deleted: a quarantined upload after its `registerPhoto`, or a deleted photo's stored size (`src/server/photos/photos.ts`). The file stays private and unserved: the bucket blocks public access and nothing presigns a read of it. A quarantined upload also expires within about a day through the lifecycle rule (`[PHOTO-7]`). No action is needed; a run of them means S3 refused the admin's deletes, which the owner sees next time as a photo that would not delete. | Orphaned stored sizes that cost something measurable, which would need a sweep (a schedule, `AGENTS.md` §3), or a publish step that serves photos. |
| `catalogue.lookup.failed` | A set search or a set lookup could not get an answer from Rebrickable (`src/server/catalogue/rebrickable.ts`, `[CAT-2]`). The line names the operation and the reason, `timeout`, `rate-limited` (a 429 after the retries), `refused-key` (a 401 or 403, or no key linked) or `upstream` (a 5xx after the retries, or an answer it could not read), never the key, the URL or the upstream's message (`[CAT-4]`). Only the signed-in owner starts a lookup, and sees the failure at once as "search unavailable" on the entry form, which still takes a typed set number (`[CAT-5]`); a `saveItem` whose lookup fails stays in the device's queue and on `/admin` (`[SYNC-8]`). That is the reasoning of `sync.mutation.failed` (brief #124, §5). Paging it would cost about $0.40 a month. | A `refused-key` that persists, which fails every search until the secret is set again (`docs/deploy.md`, step 4), if the owner finds the form's message too easy to miss; or a lookup that runs on a schedule, with no page in front of anyone. |
| `catalogue.published` | The admin published the catalogue: the snapshot under the token's path was written, its photos copied there under new random paths (`[PUB-13]`), its path invalidated on the public distribution, and the previous snapshot's files that this one doesn't hold deleted (`src/server/publish/publish.ts`, `[PUB-6]`). It records an action the owner just took, so there is nothing to act on (brief #6, §5). The line carries the request id, the file count, the bytes, and how many items and photos it published, never the token. When deleting the previous files fails, the publish still reports published and a warning with no `businessEvent` says so: the files the catalogue no longer names stay in the bucket until the next publish deletes them. | A publish the owner did not start, which would need its own signal. |
| `catalogue.republish.failed` | The republish that follows a delete of a photo, a set or a parts overview photo failed (`src/server/publish/publish.ts`, `src/server/sync/replay.ts`, `[PUB-16]`, #187): another publish held the turn for longer than the wait, or reading, writing or invalidating failed (`stage`). The delete itself is applied either way. The public catalogue still shows what was deleted until the next publish, and the previous snapshot is put back as a failed publish's is (`previousKept`, `[OPS-6]`). After the owner's own Delete on `/admin/photos` or `/admin/parts`, the page tells them at once to press Publish. A delete through the offline sync, which is how a set is deleted, answers `catalogue: 'stale'`, but the device does not show it yet (#192): until it does, the owner learns of it only by checking the catalogue or pressing Publish. The line carries the request id, never the token. A successful republish logs `catalogue.published` with `republish: true`. It is not paged: it follows a delete the owner just made, at the device, the next Publish (or the next delete) repairs it, and paging would cost about $0.40 a month. Once #192 shows the sync answer on the device, every case is an outcome the owner sees, as with `catalogue.publish.failed`. | A republish that fails repeatedly with no owner in front of a page, such as one a scheduled job starts. |
| `catalogue.token.rotated` | The admin rotated the catalogue token on `/admin/settings` (`src/server/publish/publish.ts`, `[PUB-15]`): the catalogue was published under a new token, the token stored, then every object under the old token deleted and the old path invalidated. It records an action the owner just took and sees the outcome of, so there is nothing to act on (brief #154, §5). The line carries the request id, the file, item and photo counts and `oldRemoved`, never either token. With `oldRemoved` false, logged as a warning, the old folder's deletion or its invalidation failed: the old link may keep working from the distribution's cache for up to a day, and the next publish deletes what is left in the bucket. A rotation that fails logs `catalogue.publish.failed` with `rotate: true`, and leaves the old token serving (`[OPS-6]`). Paging it would cost about $0.40 a month. | A rotation the owner did not make, which would need its own signal. |
| `catalogue.publish.failed` | A publish or a rotation (`rotate`) failed: reading the database, writing the snapshot or copying its photos (`write`), invalidating its path, or storing a rotation's new token (`token`), named by `stage`. The previous snapshot is put back, and `previousKept` says whether that worked; the owner, who started the publish, sees the outcome and the request id on `/admin` (`[OPS-6]`, decision 5). Publishes take turns (`[PUB-8]`): one that waited eight seconds for another to end fails at `stage` `read` with `PublishInProgressError`, having written nothing, and the page says another publish is running. A turn a publish failed to end is logged as a warning with no `businessEvent` and runs out by itself within three minutes, so it needs no signal of its own. Paging it would cost about $0.40 a month, a metric filter's custom metric and its alarm. | A server-side background path, such as a scheduled publish, whose failures no one would see on a page. |
| `parts.imported` | The admin imported a parts file, which replaced the parts inventory (`src/server/parts/parts.ts`, `[PARTS-3]`). It records an action the owner just took, so there is nothing to act on (brief #153, §5). The line carries the format, the number of lots, the total quantity and the request id, never a lot, a price or a remark. | An import the owner did not start, such as a scheduled one, which would need its own signal. |
| `parts.import.failed` | A parts import was refused or failed, and the inventory is unchanged (`src/server/parts/parts.ts`, `[PARTS-1]` to `[PARTS-3]`). The `reason` is the parser's code (`not-xml`, `doctype`, `invalid-lot`, …), `upload-missing`, `too-large`, or `failed` for an error on the server, with its `cause`; for a refused lot, `lot` names its place in the file and its item number, never its remark or the file's content. The upload is deleted all the same (`[PARTS-2]`). The owner, who started the import, sees the outcome on `/admin/parts` at once. Paging it would cost about $0.40 a month, a metric filter's custom metric and its alarm (brief #153, §5). | A server-side or scheduled import, whose failures no one would see on a page. |
| `parts.cleanup.failed` | An uploaded parts file could not be deleted after its import (`src/server/parts/parts.ts`). It stays private and unserved: nothing serves or presigns the `imports/` prefix, and its lifecycle rule expires it within about a day (`[PARTS-2]`). No action is needed. | A file that would stay longer than a day, such as a lifecycle rule that was removed. |
| `deploy.failed` | A failed deploy is not a cloud alarm: the deploy lane files, and keeps, one issue per environment for its failures (`K-SHIP-8`, `K-OBS-6`). | A deploy that runs outside the deploy lane, which would file no issue. |
