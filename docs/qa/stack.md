# Stack

The project's stack document (`K-LAYOUT-17`), started by `kanon init`. The sections it leaves out mean their documented defaults.

TypeScript on Node.js, the version `.nvmrc` pins, with npm. Strict `tsc --noEmit`, ESLint's flat config (`eslint.config.js`) and Vitest (`vitest.config.ts`). The toolchain and the layout are the walking-skeleton brief's decisions 11 and 12 (`docs/projects/6.md`).

## Gates

Run these from the repository root, in this order, before you push. They are exactly the commands CI's `Typecheck`, `Lint`, `Test`, `Schema check` and `Spec coverage` jobs run, in the order `.github/workflows/ci.yml` declares them (`[DEV-2]`), and `tests/tooling/ci-gates.test.ts` fails when the two disagree.

1. `npm run typecheck` — first installs SST's types into `.sst/platform` (`sst install` against `sst.types.config.ts`, which reaches no AWS and needs no deployment configuration), then runs strict `tsc --noEmit` over `src/`, `scripts/`, `tests/` and the other configuration files at the root, `eslint.config.js` included (`checkJs`), then `tsc --noEmit -p infra` over `sst.config.ts`, `sst.types.config.ts`, `infra/` and `tests/infra/`. `tests/tooling/ci-gates.test.ts` fails when a configuration file at the root is in neither project. That second project relaxes `noUncheckedIndexedAccess` and `noImplicitOverride` alone, because SST's types are TypeScript sources that don't compile under them (`infra/tsconfig.json`). npm runs the first and last steps as the `pretypecheck` and `posttypecheck` scripts.
2. `npm run lint` — ESLint over the whole repository. Under `tests/` it refuses the static ways to leave a test out: `.skip`, `.skipIf`, `.runIf`, `.todo` and `.only` on `it`, `test`, `describe` or `suite` (also further down a chain, as in `it.concurrent.skip`), importing those under another name or the test API as a namespace, and a test or hook calling its context's `skip` (`[DEV-3]`).
3. `npm test` — every Vitest test under `tests/`. The database tests need the test PostgreSQL at `DATABASE_URL`, which the project-setup hook starts in CI and in every lane (`docs/qa/test-database.md`). Without it they **fail**, by design, rather than skip (`[DEV-3]`). The run also fails when any test ends skipped or todo, however it got there (`tests/support/every-test-runs.ts`), unless you filtered it yourself with `-t`, a line number or a tag. To run them on your own machine, start the same server and export its URL:

   ```sh
   docker run -d --name test-database -e POSTGRES_USER=plinthos -e POSTGRES_PASSWORD=plinthos -e POSTGRES_DB=plinthos -p 5432:5432 postgres:16-alpine
   export DATABASE_URL=postgres://plinthos:plinthos@localhost:5432/plinthos
   ```

4. `npm run db:check` — the schema check (`[PLAT-11]`, `scripts/schema-check.ts`). It runs `drizzle-kit generate` into a copy of `drizzle/` and fails when that would add a migration, that is, when `src/db/schema/` holds a change no committed migration does; then `drizzle-kit check` over `drizzle/`. It reaches no database. When it fails, follow `## Schema changes`.
5. `node "$KANON/scripts/spec-coverage.mjs" --quiet` — the spec-coverage ratchet (#52). It fails when a test title cites an invariant ID no spec under `docs/qa/specs/` defines, when a spec names a test file that does not exist, and when the IDs the test titles cite differ from `docs/qa/specs/_locked-floor.json` in either direction. When you cite a new ID in a test title, run it once with `--write-locked` and commit the floor it rewrites: that diff is the acknowledgement. When it reports an ID the floor holds and no title cites any more, restore the citation, or take the ID out of the floor on purpose and say why in the pull request. `KANON` is the root of a Kanon checkout at the release `ci.yml` pins; the lanes set it, and CI's job sets it with Kanon's `kanon-path` action. The script installs nothing and reaches no database.

Run `npm ci` first if `node_modules/` is missing or `package-lock.json` changed.

## Schema changes

The schema is Drizzle's, in `src/db/schema/`; the migrations are in `drizzle/`, applied in order by Drizzle's migrator (`[PLAT-11]`). After you change the schema:

1. Run `npm run db:generate`. It writes the next migration and its snapshot into `drizzle/`, from the schema alone, without a database. Commit both with the schema change. For a change Drizzle can't express, such as inserting rows, run `npx drizzle-kit generate --custom --name <what-it-does>` and write the SQL into the empty migration it makes.
2. Classify every new column public or private in `src/db/schema/classification.ts` (`[PUB-3]`, `## Data isolation`).
3. Give every new table a UUID primary key that the application makes, with `.$defaultFn(() => randomUUID())`, never a sequence or a database default (`[PLAT-13]`).
4. Run the gates: `npm run db:check` must pass, and `npm test` applies every migration to an empty test database and compares the result with the schema.

Never edit a migration that has merged: production applied it on its next deploy. Change the schema again and generate a new one.

**The deploy step a pull request states for one:** none by hand. Every deploy applies the pending migrations through the Data API after `sst deploy` and before the smoke check, and a second run applies none (`[PLAT-12]`): `npx sst shell --stage production -- npm run db:migrate`, in `docs/deploy.md`'s step 5 and in the deploy hook. A pull request whose migration rewrites or drops data says so, and what the deploy does to existing rows; the walking skeleton has none.

**Expand first: a migration and the code that needs it ship in different deploys** (#78). The new server code serves from the end of `sst deploy` until the migration step finishes, and for longer when that step fails before it applies anything. So the code a deploy ships must work against the schema from before that deploy's migrations. The deploy keeps its order, `sst deploy` then the migration step (`tests/infra/deploy-hooks.test.ts`); the rule is what makes that order safe.

- **An additive change** (a new table, column, index or constraint) ships its migration in one deploy, and the code that reads or writes the new schema in a later one. The migration must also leave the code already deployed working: a new `NOT NULL` column needs a database default, Drizzle's `.default(…)`, never `$defaultFn`, which only code that names the column runs; and a new unique index or constraint must not refuse a row that code writes.
- **A destructive change** (dropping or renaming a column or a table) goes the other way round: first a deploy whose code stops using it, then the migration that removes it in a later one. The column stays in `src/db/schema/` until then, because taking it out generates the drop, but no query names it. A `NOT NULL` column with no database default takes three deploys, because the code can't leave it out of an insert until the schema marks it nullable, and that change is what generates the migration: first the migration that makes it nullable or gives it a database default, while the deployed code still writes it; then the code that stops naming it; then the drop. A rename is an add, then a drop: add the new column; then code that writes both columns and still reads the old one, with the copy of the values across, a data migration the pull request states; only a later deploy reads the new column, and the old one is then dropped as above.

A later deploy means a later release. A release carries every pull request merged before it at once, and a deployment deploys the releases in turn: `docs/deploy.md`'s step 5 checks out each release tag, and the deploy lane's `production` environment admits release tags only (`docs/deploy.md`'s `## The deploy lane`). The Reviewer holds every pull request to this rule: one whose code needs a migration that no release carries yet waits until one does, and one that drops what a release's code still uses waits for the release whose code stops using it. A release carries a commit when `git tag --contains <the commit>` names its tag or, where the tags aren't fetched, when `gh api repos/<owner>/<repo>/compare/<the tag>...<the commit> --jq .status` prints `behind` or `identical`. Three cases stay outside the rule, and the admin can fail until the migration step finishes in each: a first deploy, which has no earlier schema; a deployment that skips a release, which gets that release's migration and the code that needs it at once; and a deploy of the default branch rather than a release tag, which can carry both too.

## Data isolation

The rules a change must never regress, each with the test that proves it holds. Request changes on a pull request that weakens one of these tests or the rule it checks:

- **Every column is classified public or private, in one registry** (`[PUB-3]`): `src/db/schema/classification.ts`, held by `tests/db/classification.test.ts`. A column with no classification, in the schema or in the migrated database, fails it, and so does a value or a price classified public. Regressions: a change that lets an unclassified column through, that narrows what the test reads, or that makes a value, a price, a storage location or a note public.
- **Every admin route refuses an anonymous or forged request before its handler runs** (`[AUTH-3]`): `tests/app/admin-routes.test.ts` lists every page, Route Handler, metadata file and layout or other segment file from `src/app/` and every `'use server'` module under `src/` (`tests/support/admin-harness.ts`, #59). It asserts that each admin one is built with `adminPage`, `adminRoute` or `adminAction` (`src/server/auth/admin.ts`, #42), and sends each one a request with no cookie and with forged cookies, with and without `x-middleware-subrequest`. It fails when it finds no admin route, on a metadata file under `/admin`, on a function other than the default export or the HTTP methods exported from an admin module (`generateMetadata`, say), and on any inline Server Action, a `'use server'` inside a function, which no wrapper can guard. Regressions: a route or layout under `src/app/admin/` built without its wrapper, a wrapper that runs the handler before the check, a check moved into middleware, or a test that narrows which routes, files or requests it walks.
- **Every route is public by name or behind the admin check** (`[AUTH-4]`): the same file holds the public allow-list, `PUBLIC_ROUTES` in `tests/support/admin-harness.ts`, and fails on a route that is neither on it nor under `/admin`. Under `/admin`, the one segment file allowed without `adminPage` is the loading screen, `src/app/admin/loading.tsx` (`DATA_FREE_SEGMENTS`, `[PLAT-16]`, #203): `dataFreeProblems` in the same harness fails it when it imports anything but the message file (`src/server/` above all), imports dynamically, awaits, is async, declares a directive or names what reads a request, the environment, storage or the network (`cookies`, `headers`, `fetch`, `process`, …), and the test renders it for anonymous, forged and signed-in requests alike, requiring the same markup and no database call. Regressions: a route added to the allow-list that serves private data, an allow-list entry matched by prefix rather than by name, another kind added to `DATA_FREE_SEGMENTS`, or a name taken off `dataFreeProblems`' list.
- **Anonymous and failed requests never call the database** (`[AUTH-6]`): `tests/app/admin-routes.test.ts` and `tests/app/sign-in.test.ts` count every call that reaches for the database, for requests with no cookie, with a forged cookie, and for failed and rate-limited logins, and require none. That includes every layout and other segment file, which Next.js renders in parallel with the page whether or not the page refuses the request. A page outside `/admin`, and a segment file outside `/admin` or a Client Component one, is rendered as a whole tree with React's server renderer (`renderTree` in `tests/support/admin-harness.ts`, #67), so a read made by any component it renders counts, an async Server Component nested at any depth included. It renders once with no params or query and once with a made-up value for every name (`everyName` in `tests/support/admin-harness.ts`, #81), so that both sides of a check on whether one is there run when the check reads the name or tests for it with `in`, `Reflect.has` or as an own property. A check that enumerates the names (`Object.keys`, a spread, `new URLSearchParams(…)`) finds none in either render, so only its absent side runs, and a read only a particular value reaches is not walked. Regressions: a layout outside `/admin` that reads the database, a page or layout that is called rather than rendered, a session check that reads the database before it checks the signature, a login that looks anything up before the password matches, or a rate limiter whose state moves into Aurora.
- **The public catalogue is a snapshot, and the public distribution reaches nothing else** (`[PUB-1]`, `[PUB-2]`): `infra/snapshot.ts`, held by `tests/infra/snapshot.test.ts`. The snapshot's CloudFront distribution has one origin, the private bucket, through origin access control; the bucket blocks all public access, and its policy lets only that distribution read, only `s3:GetObject`, only under `c/`. Every response carries `X-Robots-Tag: noindex`. Public pages never query the database: they are files the publish step wrote. Regressions: a dynamic origin (a Lambda, a function URL, the admin, an API) or a second origin on the public distribution, an edge function on it, an `s3:ListBucket` or a wider prefix in its bucket policy, a website endpoint, or a weakened public access block.
- **No private field reaches a snapshot, under any setting** (`[PUB-4]`, `[PUB-5]`): `src/server/publish/projection.ts` is the one function through which publishing reads the database and the only maker of the projection the writer (`src/server/publish/snapshot.ts`) accepts. `tests/server/publish/no-private-field.test.ts` fills every private column of every table with a canary and scans every byte of every file a publish writes, for every combination of `show_values`, `selling_mode` and `selling_value_display`; `tests/server/publish/snapshot-writer.test.ts` holds the writer to the projection. The token is the snapshot's path, never content in it. A published photo is a copy of its stored sizes under a new random path in the snapshot (`[PUB-13]`, `tests/server/publish/catalogue.test.ts`): the snapshot names no stored key, and the canaries fill the photo table's keys too. Regressions: a field in the projection that a private column feeds, a snapshot that names or presigns a stored photo key, a writer that takes anything but the projection, another module under `src/server/publish/` that reads the database, or a test that narrows the tables, the columns, the encodings or the settings it covers.
- **An item's storage location is private, and an item's photos go with it** (`[ITEM-1]`, `[ITEM-5]`, `AGENTS.md` §1): `src/db/schema/collection-item.ts`, `src/db/schema/lego-set.ts` and `src/server/items/items.ts`, held by `tests/db/classification.test.ts`, `tests/server/publish/no-private-field.test.ts` and `tests/server/items/items.test.ts`. Every column of `collection_item` and `lego_set` is classified, `collection_item.storage_location` private; `[PUB-4]`'s canaries fill both tables, foreign keys included, so a storage location that reaches a snapshot fails it. `deleteItem` deletes every photo linked to the item and their stored files once that has committed, and `listItems` answers no storage location. Regressions: a storage location classified public or added to the list, a canary fill that skips a table with a foreign key, or a `deleteItem` that leaves a photo's row or files behind.
- **The service worker never caches an authenticated response** (`[SYNC-6]`): `tests/app/offline/service-worker.test.ts` runs the very script `/sw.js` serves (`src/app/sw.js/worker.ts`) against a stand-in Cache Storage and network, walks every kind of request an admin page makes, signed in, online and offline, and fails when anything is cached that is not a shell path (`/offline`, `/_next/static/`, the manifest and its icons), that is under `/admin`, or that the worker did not fetch itself with `credentials: 'omit'`; a response marked `no-store` or `private`, or one that redirected, must be refused too. Regressions: a worker that stores a navigation's or an admin route's response, that caches the page's own request rather than its own credential-free one, that widens what counts as a shell path, or a test that narrows the requests it walks or the rule it checks.
- **Logout clears the queue and the caches, after a warning** (`[SYNC-9]`): `tests/app/offline/sign-out.test.ts` and `tests/app/offline/client.test.ts` hold `src/app/_offline/sign-out.ts` and the sign-out button to it: with mutations queued, logout names how many are unsynced and, once confirmed, empties the IndexedDB queue and deletes every cache of the origin before it posts `/admin/logout`. A queue that is there but fails to open, or whose open never settles, is never taken for an empty one: logout warns that unsynced changes may be on it and, once confirmed, deletes its database; when that fails too, it refuses to sign out and keeps the caches, as it does with no network (#79). When any other step on the device fails, counting or emptying the queue or deleting the caches, it refuses to sign out too and tells the admin they are still signed in, never doing nothing and saying nothing (#99). The queue is the one store on the device that outlives a session (`[SYNC-8]`), so this is the step that takes private data off it. The queue must never hold a server record in the first place: `tests/app/offline/queue.test.ts` holds it to keeping what the server said about a mutation it stopped, never the record a conflict returned. Regressions: a logout that skips the clearing, that clears only some caches, that signs out without the warning, that takes a queue it could not open for an empty one, that signs out with a queue it could not delete, that posts the logout or fails silently when a step after the open fails, or a change that lets the queue keep a server record a conflict returned.
- **A photo is re-encoded on the server, every size of it, and the uploaded bytes are never kept** (`[PHOTO-3]`, `[PHOTO-4]`, `AGENTS.md` §1): `src/server/photos/photos.ts` and `src/server/photos/reencode.ts`, held by `tests/server/photos/register-photo.test.ts`. It puts a made-up JPEG carrying EXIF GPS, a camera model, XMP and an orientation straight into the quarantine, runs `registerPhoto` through the offline-sync replay, and fails when any stored size carries EXIF, XMP, IPTC, an ICC profile or any made-up value, is not upright, or when the quarantined object is still there. It also fails when the sizes are written after the photo's row commits, or when an already-applied, conflicting, refused or failed `registerPhoto` leaves its quarantined object behind (#9). Regressions: a stored size written from the uploaded bytes, `keepMetadata`, `withMetadata` or `keepExif` on an output, a decoder other than JPEG's, a path through `registerPhoto` that skips the registry's `settled`, or a test that narrows the metadata, the sizes or the outcomes it checks.
- **Stored photos are private, behind random keys and short-lived links** (`[PHOTO-6]`): `infra/photos.ts`, `src/server/photos/keys.ts` and `src/server/photos/storage.ts`, held by `tests/infra/photos.test.ts`, `tests/server/photos/storage.test.ts` and `tests/server/photos/register-photo.test.ts`. The photo bucket blocks all public access, is the origin of no distribution, and its policy only refuses; every key is 256 random bits the server makes, holding nothing the client sent; the admin sees a photo only through a presigned GET of a stored size that expires within 15 minutes. Regressions: a CloudFront origin, a website endpoint or an `Allow` statement on the photo bucket, a key derived from the client's id or the photo's hash, or a presigned URL that lives longer. The `trash/` prefix ([PHOTO-9], `tests/infra/photos.test.ts`, `tests/server/photos/storage.test.ts`) is held the same way: the app may only write into it, nothing reads, serves or presigns it, and the bucket stays unversioned. Versioning would keep every deleted quarantine upload as a hidden old version.
- **The quarantine is presigned only to a valid session, expires, and is never served** (`[PHOTO-7]`): `infra/photos.ts`, `src/server/photos/storage.ts` and `src/app/admin/api/photos/uploads/route.ts`, held by `tests/infra/photos.test.ts`, `tests/server/photos/storage.test.ts` and `tests/app/admin-photo-uploads-route.test.ts`. The presign route is an admin route; the upload it signs pins its key under `quarantine/`, caps its size and expires within 15 minutes; a lifecycle rule expires everything under `quarantine/` after one day; the storage refuses a presigned read of any key under it, and the CORS rule lets only the admin's origin post. Regressions: a read or an origin on the quarantine prefix, a longer lifecycle on it, an upload presigned outside it or without its cap, or a CORS rule that allows another origin or method.
- **A parts file is never kept, and nothing private in it is stored** (`[PARTS-1]`, `[PARTS-2]`, brief #153): `src/server/parts/parse.ts`, `src/server/parts/parts.ts`, `src/server/photos/storage.ts` and `infra/photos.ts`, held by `tests/server/parts/parse.test.ts`, `tests/server/parts/import.test.ts`, `tests/app/admin-parts-uploads-route.test.ts` and `tests/infra/photos.test.ts`. The parser returns six fields of a lot and never a remark, a comment or anything else, refuses every entity declaration and every DTD but the bare one older BrickStore files carry, and parses with entity processing off, so an XXE file reads nothing. The file arrives through a presigned upload into `imports/`, which the presign route signs only for a valid session, with a cap and a 10-minute expiry; nothing serves, writes or presigns a read under it, its lifecycle rule expires it after a day, and `importPartsFile` deletes the upload whatever it comes to. Regressions: a parser that returns or stores another field, that resolves an entity or reads a DTD, an import that keeps the upload on any outcome, a read or an origin on `imports/`, or a longer lifecycle on it.
- **The parts' values are private, and the publish step may read only the summary** (`[PARTS-4]`, `[PARTS-5]`, `[PUB-4]`): `src/db/schema/parts.ts`, `src/db/schema/classification.ts` and `src/server/parts/summary.ts`, held by `tests/db/classification.test.ts`, `tests/server/parts/import.test.ts` and `tests/server/publish/no-private-field.test.ts`. Every column of `parts_import` and `parts_lot` is classified; only `parts_import.lots` and `parts_import.quantity` are public, `unit_price` and `total_value` are private, and every lot column stays private until the valuation milestone (#5). `[PUB-4]`'s canaries fill both tables, and its key check needs their private columns named apart from any public one, which is why they are `file_format`, `lot_condition` and `lot_quantity`. `readPartsSummary` answers the counts and the overview photos' keys, never a price or a lot. Regressions: a price or a value classified public, a lot column made public before #5, a private parts column renamed to a public column's name, or a `readPartsSummary` that answers more.

## Generated files

- `package-lock.json` — npm writes it from `package.json`. After a merge conflict in it, resolve `package.json` first, take either side of the lockfile, then run `npm install --package-lock-only` and commit the result. Never edit it by hand.
- `drizzle/*.sql` and `drizzle/meta/` — `npm run db:generate` writes each migration and its snapshot from `src/db/schema/`; only a custom migration's SQL is written by hand. After a merge conflict there, keep `main`'s migrations as they are, delete your branch's generated migration and its snapshot and their entry in `drizzle/meta/_journal.json`, then run `npm run db:generate` again and commit the result. Never renumber or edit a merged migration.

## Code areas

- `src/` — code: the application, Next.js under `src/app/`, the typed service core under `src/server/` and the schema and client under `src/db/`
- `infra/` — code: the SST modules `sst.config.ts` composes
- `scripts/` — code: the deploy's migration step and the schema check, which run outside the application
- `tests/` `vitest` — tests: unit, integration and tooling tests, and their support code under `tests/support/`
