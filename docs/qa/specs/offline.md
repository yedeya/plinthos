# Offline entry

Entering data without a signal: the installable admin shell, the queue on the owner's device, and the offline-sync endpoint that replays it through the typed service core (`AGENTS.md` §4, `HANDOVER.md` §10.7). Seeded by the walking-skeleton project (#6), whose decision 2 put offline entry in the skeleton. Every clause is `[seed]` until a human promotes it (`K-SPEC-8`).

**Id prefix:** `SYNC`

## The sync endpoint

- `[SYNC-1]` `[seed]` The offline-sync endpoint is an admin route that takes a batch of queued mutations, validates each one with the zod schema of the service function it names, and applies it only by calling that service function with the session's `AdminContext`; a mutation that names no registered service function is refused as invalid.
- `[SYNC-2]` `[seed]` Every mutation carries a client-generated UUID, and the record that the id was applied is written in the same transaction as the change it made; a mutation whose id was already applied with the same payload changes nothing and returns the first result. A mutation's payload is its input and base version, unless its service function's clause names the part of the input it is compared by, as `[PHOTO-2]` names the photo's hash.
- `[SYNC-3]` `[seed]` A mutation whose id was already applied with a different payload, or whose base version differs from the server's current version of the record it changes, is not applied; the endpoint returns it as a conflict with the server's current version, and logs the `businessEvent` `sync.conflict` with the mutation id and the service function's name and never the payload.
- `[SYNC-4]` `[seed]` The mutations of a batch are applied in the order the client queued them, each in its own transaction, and the response names each one's outcome (applied, already applied, conflict, invalid, failed or not attempted); an invalid one that its service function refused after reading its input also carries that refusal's code, such as `[PHOTO-8]`'s `upload-missing`. The first mutation that is not applied, a conflict, an invalid or a failed one, ends the batch: every mutation after it is answered as not attempted, is not run and records nothing. An already-applied mutation counts as applied and does not end the batch. A mutation that fails on the server logs the `businessEvent` `sync.mutation.failed` with its id.
- `[SYNC-10]` `[seed]` One batch carries at most `MAX_PHOTOS_PER_BATCH` `registerPhoto` mutations, one constant that the client and the endpoint both read, so that a batch finishes inside the admin's server function's timeout however many photos are queued (#95). The client ends a batch before the photo that would pass the cap and uploads only that batch's photos before it sends it; the endpoint refuses a longer batch whole, running none of it. The server function's timeout is set explicitly, no longer than CloudFront's 60-second origin response timeout and shorter than the client's `REPLAY_TIMEOUT_MS`, and the cap times the per-photo budget `PHOTO_BUDGET_MS` is shorter than that timeout.
- `[SYNC-11]` `[seed]` One batch's mutations together, set lookups included, run on the server for no longer than `BATCH_BUDGET_MS`, which is shorter than the admin's server function's timeout and holds `MAX_PHOTOS_PER_BATCH` photos at `PHOTO_BUDGET_MS` each (#138). Each replayable mutation declares its worst case: `PHOTO_BUDGET_MS` for `registerPhoto`, its set lookup's budget plus `MUTATION_BUDGET_MS` for `saveItem` (`[ITEM-4]`), and `MUTATION_BUDGET_MS` for any that declares none, none of them longer than `BATCH_BUDGET_MS`. The endpoint always runs a batch's first mutation; it starts each later one only when the time the batch has taken plus that mutation's worst case is within `BATCH_BUDGET_MS`. The first that is not is answered as not attempted, and so is every mutation after it, and the endpoint logs the `businessEvent` `sync.batch.out_of_time`. A client whose batch comes back as applied mutations followed by not-attempted ones sends the rest at once in its next batch; one whose batch comes back with its first mutation not attempted stops, and sends nothing again until the next trigger.

## The installable shell

- `[SYNC-5]` `[seed]` The admin is an installable web app: it serves a web app manifest and registers a service worker, and an installed admin with no network opens to its shell and its queue. The shell is a prerendered document at `/offline` that carries no data, which the service worker precaches without credentials and serves when a navigation fails for want of a network.
- `[SYNC-6]` `[seed]` The service worker caches only the app shell and the static build assets; it never caches a response to a request that carries the session cookie or a response from an admin route handler, and a test of its fetch handler fails when one is cached.

## The queue

- `[SYNC-7]` `[seed]` A change made without a network is kept in an IndexedDB queue on the device, survives a reload and a restart of the browser, and is replayed when the network returns and when the admin is opened; the client asks the browser for persistent storage.
- `[SYNC-8]` `[seed]` A queued mutation leaves the queue only when the server answers it as applied or already applied. When replay meets an ended session, it stops, sends the admin to the login, and resumes after sign-in. A conflict or an invalid mutation is held at once: it stays in the queue and is shown on `/admin` until the admin retries or discards it. The one exception is an invalid `registerPhoto` that carries `[SYNC-4]`'s refusal code `upload-missing`: the client uploads the photo's bytes again and resends it under the same id, once per replay, as `[PHOTO-8]` says, and holds it only when that comes back `upload-missing` too; this keeps any failure count it carries. A failed mutation is retried automatically, only at a trigger (the admin opening or the network returning) and only once its backoff has passed, measured on the device's clock from the failure and due at once if that clock reads earlier than the failure, so a clock correction never holds it for more than one backoff after the correction, up to `MAX_FAILED_ATTEMPTS` failures; then it is held on `/admin` for retry or discard like a conflict. While a mutation waits or is held, every mutation queued after it stays queued behind it, in order.
- `[SYNC-9]` `[seed]` Logout with a non-empty queue says how many mutations are not yet synced, and once the admin confirms, clears the queue and every cache the service worker holds.
