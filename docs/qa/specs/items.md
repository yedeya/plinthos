# Collection items

What the owner logs: one item per set they hold, with its condition, completeness, notes, quantity, private storage location and photos (`HANDOVER.md` §4.1), and, since the Owner's decisions of 2026-11-02 (#202, superseding `HANDOVER.md` §10.10), minifigures, bulk or unsorted lots and other LEGO items beside the sets. Seeded by the set-entry project (#124). No item is published yet: the public snapshot gains items with the public catalogue milestone. Values and prices belong to the valuation milestone. Every clause is `[seed]` until a human promotes it (`K-SPEC-8`).

**Id prefix:** `ITEM`

## The record

- `[ITEM-1]` `[seed]` An item is a `collection_item` row with a UUID the client makes (`[PLAT-13]`), a `kind` (`[ITEM-10]`), a set number for a set or a name for any other kind, an optional reference number, `condition` (`SEALED`, `USED_WITH_BOX` or `USED_NO_BOX`), `complete` with an optional free-text note of what is missing, `has_instructions`, a description of at most 2,000 characters, a quantity from 1 to 999, a storage location of at most 200 characters, a version, and when it was created and last changed. Every one of its columns is classified in the `[PUB-3]` registry, and `storage_location` is private.
- `[ITEM-2]` `[seed]` `saveItem` creates or updates an item, and `deleteItem` deletes one. Both are typed service functions with zod-validated input, take an `AdminContext` (`AGENTS.md` §4), and are registered sync mutations, so the entry form, the offline queue and later tools all go through them (`[SYNC-1]`).
- `[ITEM-3]` `[seed]` An item is a versioned record (`[SYNC-3]`). `saveItem` carries `baseVersion`, null to create. A version that is not the item's current one is a `conflict`, answered with the server's item. Two creates of the same item id are a conflict and never an overwrite: the item's primary key refuses the second, and the replay answers it as a `version` conflict rather than `failed`.
- `[ITEM-4]` `[seed]` When `saveItem` saves a `SET` whose set number `lego_set` doesn't hold, it looks the set up on Rebrickable inside its own time budget (`[CAT-2]`, `[CAT-3]`). A set number Rebrickable doesn't know is refused as invalid with the code `unknown-set`, and the item is held on `/admin` for the owner to correct. A Rebrickable failure answers the mutation as `failed`, so the phone retries it with backoff (`[SYNC-8]`). A set is never stored without its catalogue row. No other kind is looked up.
- `[ITEM-10]` `[seed]` An item's `kind` is `SET`, `MINIFIG`, `BULK` or `OTHER`; the column's database default is `SET`, so every item stored before the kinds is a set, and a `saveItem` with no `kind`, as every one queued before them, saves a set. A `SET` needs a set number, resolved as `[ITEM-4]` says. Any other kind needs a name, plain text of 1 to 200 characters once trimmed, and is never looked up, so it saves offline and through the queue with no network. Every kind may have a reference number of at most 40 characters, such as a figure number `sw0001` or a BrickLink item number. Only a `BULK` lot may have an approximate piece count, 1 to 1,000,000, and an approximate weight in grams, 1 to 10,000,000. Completeness and instructions are required for a set and optional for any other kind, stored as null when not stated. A database check refuses a `SET` without a set number and any other kind without a name. An edit may change the kind, and leaves no set number on a non-set and no bulk lot's numbers on another kind.
- `[ITEM-5]` `[seed]` `deleteItem` deletes the item and every photo linked to it. Each photo's stored sizes move to the trash after the transaction commits, as `deletePhoto`'s do (`[PHOTO-9]`).

## Photos

- `[ITEM-6]` `[seed]` A photo belongs to at most one item. `registerPhoto` accepts an optional item id and position, and links the photo when the item exists. An item's photos have an order, and an item with photos has exactly one cover, which is the first photo until the owner picks another. `setItemPhotos` sets the order and the cover of an item's photos, and refuses a photo that isn't the item's. Deleting the cover makes the next photo the cover.
- `[ITEM-7]` `[seed]` On the phone, a new item's `saveItem` is queued before its photos' `registerPhoto` mutations, which carry the item's id, so an item and its photos entered offline sync in that order and arrive linked.

## Screens

- `[ITEM-8]` `[seed]` `/admin` lists the owner's items, newest first. Each shows a thumbnail, by default the set's stock image from the catalogue, else its cover thumbnail through a presigned URL (`[PHOTO-6]`), and its set number, name, condition and quantity, and the list filters by set number, name or reference number as the owner types. A minifigure, bulk lot or other item shows its own name and a small kind label, and never a stock image, which is a set's alone. `listItems` answers no storage location. Items still in the device's queue are listed too, marked as not synced.
- `[ITEM-9]` `[seed]` The entry form is one screen: one field for a set number or name, photos, condition, completeness, instructions, quantity, description and storage location. The field searches from 2 characters, about 1 second after the last keystroke when the text is digits (optionally with a `-n` variant) and about 0.5 seconds otherwise, and newer text aborts the search before it, whose answer is never shown. Text that reads as a set number saves without a pick, as the result that is exactly that set when the results hold it, otherwise as typed and resolved when it syncs (`[ITEM-4]`); a name with no set picked is refused under the field. With no set chosen and text that is not a set number, the form offers to log the item as a Minifigure, a Bulk lot or Other, and **Not a set?** beside the field always does (`[ITEM-10]`): the set field gives way to the kind choice, a Name field prefilled with the typed text, a reference number and, for a bulk lot, the approximate piece count and weight; completeness and instructions start as not stated; **It’s a set** goes back. Each field is checked inline. **Save & add next** queues the item and clears the form for the next one, keeping the kind, the condition and the storage location. The same form works on the offline shell and on a device without a network, where the field sends no request (`[SYNC-6]`: the shell stays data-free). An existing item is edited through the same form, online, and a stale edit meets the conflict rule above.
