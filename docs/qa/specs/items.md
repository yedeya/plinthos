# Collection items

What the owner logs: one item per set they hold, with its condition, completeness, notes, quantity, private storage location and photos (`HANDOVER.md` §4.1), and, since the Owner's decisions of 2026-11-02 (#202, superseding `HANDOVER.md` §10.10), minifigures, bulk or unsorted lots and other LEGO items beside the sets. Seeded by the set-entry project (#124). The themes, filters and sort are the item-list filters project's (#251). No item is published yet: the public snapshot gains items with the public catalogue milestone. Values and prices belong to the valuation milestone. Every clause is `[seed]` until a human promotes it (`K-SPEC-8`).

**Id prefix:** `ITEM`

## The record

- `[ITEM-1]` `[seed]` An item is a `collection_item` row with a UUID the client makes (`[PLAT-13]`), a `kind` (`[ITEM-10]`), a set number for a set or a name for any other kind, an optional reference number, `condition` (`SEALED`, `USED_WITH_BOX` or `USED_NO_BOX`), `complete` with an optional free-text note of what is missing, `has_instructions`, a description of at most 2,000 characters, a quantity from 1 to 999, a storage location of at most 200 characters, a version, and when it was created and last changed. Every one of its columns is classified in the `[PUB-3]` registry, and `storage_location` is private.
- `[ITEM-2]` `[seed]` `saveItem` creates or updates an item, and `deleteItem` deletes one. Both are typed service functions with zod-validated input, take an `AdminContext` (`AGENTS.md` §4), and are registered sync mutations, so the entry form, the offline queue and later tools all go through them (`[SYNC-1]`).
- `[ITEM-3]` `[seed]` An item is a versioned record (`[SYNC-3]`). `saveItem` carries `baseVersion`, null to create. A version that is not the item's current one is a `conflict`, answered with the server's item. Two creates of the same item id are a conflict and never an overwrite: the item's primary key refuses the second, and the replay answers it as a `version` conflict rather than `failed`.
- `[ITEM-4]` `[seed]` When `saveItem` saves a `SET` whose set number `lego_set` doesn't hold, it looks the set up on Rebrickable inside its own time budget (`[CAT-2]`, `[CAT-3]`). A set number Rebrickable doesn't know is refused as invalid with the code `unknown-set`, and the item is held on `/admin` for the owner to correct. A Rebrickable failure answers the mutation as `failed`, so the phone retries it with backoff (`[SYNC-8]`). A set is never stored without its catalogue row. No other kind is looked up.
- `[ITEM-10]` `[seed]` An item's `kind` is `SET`, `MINIFIG`, `BULK` or `OTHER`; the column's database default is `SET`, so every item stored before the kinds is a set, and a `saveItem` with no `kind`, as every one queued before them, saves a set. A `SET` needs a set number, resolved as `[ITEM-4]` says. Any other kind needs a name, plain text of 1 to 200 characters once trimmed, and is never looked up, so it saves offline and through the queue with no network. Every kind may have a reference number of at most 40 characters, such as a figure number `sw0001` or a BrickLink item number. Only a `BULK` lot may have an approximate piece count, 1 to 1,000,000, and an approximate weight in grams, 1 to 10,000,000. Completeness and instructions are required for a set and optional for any other kind, stored as null when not stated. A database check refuses a `SET` without a set number and any other kind without a name. An edit may change the kind, and leaves no set number on a non-set and no bulk lot's numbers on another kind.
- `[ITEM-5]` `[seed]` `deleteItem` deletes the item and every photo linked to it. Each photo's stored sizes move to the trash after the transaction commits, as `deletePhoto`'s do (`[PHOTO-9]`).

## Themes

- `[ITEM-11]` `[seed]` A `lego_set` row holds, beside the theme's own name, two nullable columns: `theme_id`, Rebrickable's id for that theme, and `top_theme`, the name of its top-level theme. The top-level theme is the root reached by following each theme's parent in Rebrickable's theme tree (`/lego/themes/`), and is the theme itself when it has no parent, so a set under a sub-theme of Ninjago has Ninjago as its top-level theme. The migration that adds them only adds, and a row stored before them holds null until the backfill fills it (`[ITEM-13]`). `theme_id` is classified private, an internal key, and `top_theme` public, a public fact about the set, though no snapshot carries it yet (`[PUB-3]`).
- `[ITEM-12]` `[seed]` Every set a lookup or a search stores carries its theme id and its top-level theme, replacing older ones (`[CAT-3]`). The client reads the parents from Rebrickable's theme list, kept in memory for the life of the instance as the theme names are, so a set whose theme is cached costs no extra request. A theme whose root can't be read leaves `top_theme` null rather than failing the lookup.
- `[ITEM-13]` `[seed]` `backfillThemes`, a typed service function, fills the theme id and the top-level theme of every set that an item names and whose `top_theme` is null. It reads Rebrickable's theme list once. A set whose stored theme name occurs once in the tree takes that theme, with no further request. A set whose name occurs under more than one parent, or nowhere, is looked up by its set number, one request each, through the one client (`[CAT-2]`). A set Rebrickable can't answer for keeps a null top-level theme, and the next run tries it again. A run with nothing to fill makes no request. It runs in the migration step, after the migrations (`docs/deploy.md` step 5), and its failure never fails that step. It logs `catalogue.themes.backfilled` with how many sets it filled by name, filled by lookup, and left unknown.

## Photos

- `[ITEM-6]` `[seed]` A photo belongs to at most one item. `registerPhoto` accepts an optional item id and position, and links the photo when the item exists. An item's photos have an order, and an item with photos has exactly one cover, which is the first photo until the owner picks another. `setItemPhotos` sets the order and the cover of an item's photos, and refuses a photo that isn't the item's. Deleting the cover makes the next photo the cover.
- `[ITEM-7]` `[seed]` On the phone, a new item's `saveItem` is queued before its photos' `registerPhoto` mutations, which carry the item's id, so an item and its photos entered offline sync in that order and arrive linked.

## Screens

- `[ITEM-8]` `[seed]` `/admin` lists the owner's items, newest first unless sorted otherwise (`[ITEM-16]`). Each shows a thumbnail, by default the set's stock image from the catalogue, else its cover thumbnail through a presigned URL (`[PHOTO-6]`), and its set number, name, condition and quantity, and the list filters by set number, name or reference number as the owner types, and by the filters of `[ITEM-14]`. A minifigure, bulk lot or other item shows its own name and a small kind label, and never a stock image, which is a set's alone. `listItems` answers no storage location. Items still in the device's queue are listed too, marked as not synced.
- `[ITEM-9]` `[seed]` The entry form is one screen: one field for a set number or name, photos, condition, completeness, instructions, quantity, description and storage location. The field searches from 2 characters, about 1 second after the last keystroke when the text is digits (optionally with a `-n` variant) and about 0.5 seconds otherwise, and newer text aborts the search before it, whose answer is never shown. Text that reads as a set number saves without a pick, as the result that is exactly that set when the results hold it, otherwise as typed and resolved when it syncs (`[ITEM-4]`); a name with no set picked is refused under the field. With no set chosen and text that is not a set number, the form offers to log the item as a Minifigure, a Bulk lot or Other, and **Not a set?** beside the field always does (`[ITEM-10]`): the set field gives way to the kind choice, a Name field prefilled with the typed text, a reference number and, for a bulk lot, the approximate piece count and weight; completeness and instructions start as not stated; **It’s a set** goes back. Each field is checked inline. **Save & add next** queues the item and clears the form for the next one, keeping the kind, the condition and the storage location. The same form works on the offline shell and on a device without a network, where the field sends no request (`[SYNC-6]`: the shell stays data-free) and searches the set index the device holds, when it holds one (`[CAT-11]`). An existing item is edited through the same form, online, and a stale edit meets the conflict rule above.

## Filters and sort

- `[ITEM-14]` `[seed]` `/admin` filters the item list by theme, condition, completeness, instructions, kind and what needs attention (`[ITEM-15]`). The theme options are the top-level themes of the listed sets, by name (`[ITEM-11]`), and *Theme not known* for a set without one. A non-set matches no theme option. The condition options are sealed, used with box and used without box. Completeness and instructions each offer yes, no and *not recorded*, and each filter's *not recorded* matches an item whose value in that field is null (`[ITEM-10]`), whatever its other field holds. The kind options are set, minifigure, bulk lot and other. An item matches a filter when it has any of the options chosen in it, and is listed when it matches every filter and the text filter (`[ITEM-8]`), which also matches the set's theme and top-level theme. Filtering runs in the browser over the list the page loaded and sends no request, so it answers as the owner taps and keeps working when the network drops.
- `[ITEM-15]` `[seed]` The *needs attention* filter has two options. *No value*: the item has neither a BrickLink value nor a manual value (`[VAL-5]`). *Incomplete, nothing noted*: the item is marked not complete and has no note of what is missing. They are the admin's alone, like the values they read (`[VAL-7]`). There is no *no photo* option, by the Owner's choice (#251), and no *hidden from the catalogue* option, because no item can be hidden from the catalogue.
- `[ITEM-16]` `[seed]` The list sorts by date added, newest first, which is the default, by value, highest first, or by year, newest first. An item with no value, or a non-set, which has no year, comes after every item that has one, newest added first among them. Items still in the device's queue stay above the list, in the queue's order.
- `[ITEM-17]` `[seed]` Each filter option shows how many items the list would show with that option chosen alone in its filter and every other filter as it is. The count is of items, not of their quantities, and every item counts under exactly one option of the condition, completeness, instructions and kind filters, *not recorded* included, so each of those filters' counts add up to what the list would show without it. An option that would show none is still offered, with 0, and stays choosable.
- `[ITEM-18]` `[seed]` The filters, the text filter and the sort are kept in the page's query string, updated in place without a navigation or a request, so going back from an item, a reload and a bookmark show the same list. An unknown or malformed value in the query string is ignored, never an error, and the default list has no query string.
- `[ITEM-19]` `[seed]` A new item still in the device's queue is filtered on what the queue holds: its text, kind, condition, completeness and instructions. The queue holds no theme, so a queued set matches every theme option, and the theme filter never hides a queued set. Every other filter applies to a queued item on the fields it holds, like any item. A queued new item has no value, so it matches *No value*. A queued change to a stored item is filtered as the stored item, which the list shows marked (`[ITEM-8]`). The counts include queued items the same way.
- `[ITEM-20]` `[seed]` `listItems` reads the items in pages, ordered by when each was added and then by id, so no Data API answer passes its 1 MB cap however many items there are. For each item it answers what the list, its filters and its sort need: the top-level theme and the theme, the year, completeness, instructions, and whether a note of what is missing exists (never the note). It still answers no storage location.
