# The public snapshot

How the public catalogue is separated from private data by construction: a static snapshot that one publish step generates, served from S3 by CloudFront, never from the database (`AGENTS.md` §1, `HANDOVER.md` §4.3 and §8). Seeded by the walking-skeleton project (#6). Every clause is `[seed]` until a human promotes it (`K-SPEC-8`).

**Id prefix:** `PUB`

## Public and private, by construction

- `[PUB-1]` `[seed]` The public catalogue is served by a CloudFront distribution whose only origin is the private snapshot bucket, reached through origin access control; it has no dynamic origin, and the bucket blocks all public access.
- `[PUB-2]` `[seed]` Every response from the public distribution carries `X-Robots-Tag: noindex`, and a request for `/`, for `/c/` or for an unknown token is answered without a listing of the bucket.
- `[PUB-3]` `[seed]` Every column of the database schema is classified as public or private in one registry, a column with no classification fails the test, and every value, price and asking price is classified private under every setting: whether the catalogue shows one is the settings' decision, which the publish step's projection applies (`[PUB-17]` to `[PUB-20]`), never a column's classification.
- `[PUB-4]` `[seed]` No private field's value appears anywhere in a generated snapshot, except the values and asking prices the settings show, each only in the combinations and the fields `[PUB-17]` to `[PUB-20]` show it in: the test fills every private field with a canary value, takes the values from a reader whose every amount is a canary too, and scans every byte of every file the publish step writes, in every encoding it checks, for every combination of `show_values`, `selling_mode` and `selling_value_display`. A shown canary must be in `catalogue.json` where the contract puts it and absent from every combination that doesn't show it; every other canary, a stored quote, an override and the parts file's own prices included, is absent under every combination. A private field too narrow for a canary, a value adjustment, takes each of two values within every group of combinations that show the same, and every combination in a group writes the same bytes, so neither it nor a switch changes anything but what is shown.
- `[PUB-5]` `[seed]` The snapshot writer accepts only the public projection's type, and the publish step reads the database only through the one function that builds that projection: no other module under `src/server/publish/`, whatever its extension, reaches the database, by its own imports or through any module they lead to.

## The publish step

- `[PUB-6]` `[seed]` `publishCatalogue` is a typed service function with zod-validated input that only an authenticated admin can call; it writes the catalogue's content, the snapshot of what the public projection holds, under `/c/{token}/`, invalidates only that path in CloudFront, and logs the `businessEvent` `catalogue.published` or `catalogue.publish.failed`.
- `[PUB-7]` `[seed]` The catalogue token holds at least 128 bits from a cryptographically secure generator and is URL-safe.
- `[PUB-8]` `[seed]` Publishes take turns: when two overlap, the files under `/c/{token}/` are one publish's whole, those of the last to report `published`; a publish that fails puts back the files of the publish before it, never those of one that overlapped it and succeeded; and a publish that waits too long for its turn writes nothing and says another publish is running.

## The catalogue

Seeded by the public-catalogue project (#154). The catalogue shows no value, price or total unless the settings show them, as `[PUB-17]` to `[PUB-20]` decide; every one of those settings is off by default and private.

- `[PUB-9]` `[seed]` `/admin/settings` holds the catalogue's intro text and contact text, each plain text of at most 2,000 characters, saved through a typed service function. Both are public and are classified so in `[PUB-3]`'s registry. They reach the catalogue only at the next publish, and are rendered escaped, never as HTML.
- `[PUB-10]` `[seed]` The catalogue's landing page shows the intro text, the contact text, and a summary: how many sets there are, how many other items when there are any (`[ITEM-10]`), how many items there are per condition, how many items in all (each item's quantity counted), and how many loose parts and lots, when there are any. Every number is computed from the snapshot's own data, never by a query, so the summary can't count a field the snapshot doesn't hold.
- `[PUB-11]` `[seed]` The catalogue lists every item in a grid: its thumbnail (the set's stock image by default, else the owner's cover), set number, name, theme, year and condition. A minifigure, bulk lot or other item (`[ITEM-10]`) shows its reference number in place of a set number, its name, what it is in place of the theme and year, a bulk lot's approximate pieces and weight, and never a stock image. Filters by condition, by theme and, once the catalogue holds more than one kind, by kind, and sorting by set number, year or name, run in the visitor's browser over the snapshot's data; by set number, and in the HTML's own order, every item that is not a set comes after the sets, by name, and by year after those with one. `catalogue.json` (since format 3) carries each item's `kind`, its display name, `refNo`, `approxParts` and `approxWeightG`, and `setNum`, `theme`, `year`, `numParts` and `stockImageUrl` are null for a non-set. Thumbnails load lazily, and every image has alt text.
- `[PUB-12]` `[seed]` Each item has a detail page in the snapshot: its photos as a gallery, the stock image, its set number, name, theme, year and piece count, condition, completeness and what is missing, whether it has instructions, its description and its quantity, and its id, the random UUID that names its page, `/c/{token}/s/{id}/`. A minifigure, bulk lot or other item's page shows what it is, its name, its reference number, a bulk lot's approximate pieces and weight, and its completeness and instructions only when the owner stated them, and no theme, year, piece count or stock image. Nothing else about the item is published: never its storage location, an override's amount as such, or when it was created or changed; a value only as `[PUB-17]` and `[PUB-18]` show it, and the split view it is in only as `[PUB-19]` shows it.
- `[PUB-13]` `[seed]` A published photo is a public copy, never the private file. At each publish, every photo of a published item, and every overview photo of the parts lot, is copied from its private stored sizes into the snapshot under `/c/{token}/` with a new random key, and the snapshot names only those keys. A photo deleted since the last publish is absent from the next snapshot. The public copies are WebP, re-read from the already metadata-free stored sizes (`[PHOTO-4]`), and have no metadata either.
- `[PUB-14]` `[seed]` The parts section of the catalogue shows how many lots and loose parts there are, and the parts lot's overview photos, and no price, value or lot list unless `[PUB-17]` to `[PUB-20]` show them: with selling mode off and values hidden, none.
- `[PUB-15]` `[seed]` Rotating the catalogue token on `/admin/settings`, after a confirmation, makes a new token, publishes the catalogue under it, then deletes every object under the old token's prefix and invalidates it, so the old link stops working (`AGENTS.md` §1). A rotation that fails before the new snapshot is written leaves the old one serving (`[OPS-6]`).
- `[PUB-16]` `[seed]` A delete of a photo, a set or a parts-lot overview photo, while a catalogue is published, republishes it in the publish's turn (`[PUB-8]`), so what was deleted and its public photo copies leave the public site within seconds (`[PUB-13]`): once after a sync batch however many deletes it applied, and after the admin's own Delete. A failed republish never fails the delete, and `catalogue.republish.failed` is logged. After the admin's own Delete on `/admin/photos` or `/admin/parts`, the page says the catalogue still shows it; through the offline sync, the batch's answer carries `catalogue: 'stale'`, and the device's header says so on every admin page until the admin dismisses it, a later sync replaces it or a publish from that tab succeeds (#192). With no catalogue published, nothing is published.

## Values and selling mode

Seeded by the valuation project (#207), from `HANDOVER.md` §4.3. Whether a value reaches the catalogue depends only on the current settings, never on whether one is stored.

- `[PUB-17]` `[seed]` With selling mode off, the catalogue shows market values only while **Show values** is on: each item's value with "estimated, as of {date}", a total per segment on the landing page, and sorting by value. With it off, the snapshot holds no value, no total, no subtotal and no order derived from a value, and `[PUB-4]`'s canary test proves it under every combination of the settings.
- `[PUB-18]` `[seed]` With selling mode on, `selling_value_display` alone decides what is shown and **Show values** is ignored: `ASKING` (the default when selling mode is first turned on) shows the asking prices per segment and overall and no market value anywhere; `MARKET` shows market values as **Show values** does; `BOTH` shows both. Sorting by value uses only per-item values that are shown, so with `ASKING` there is none. An asking price entered in selling mode is not published once selling mode is off.
- `[PUB-19]` `[seed]` With selling mode on, the catalogue adds split views, sealed sets only, used sets only and loose parts only, each with its own subtotal of the values the display shows, so a buyer interested in part of the lot sees a coherent offer.
- `[PUB-20]` `[seed]` With selling mode on, the catalogue offers a downloadable parts list, as CSV and as BrickLink XML, generated from the imported lots and never from the uploaded file. It holds each lot's item type, item number, colour, condition and quantity, and a per-lot unit price, the lot's value by `[VAL-6]` divided by its quantity, only when the display shows market values; never a remark, a comment or anything the import didn't keep (#5).
